# 011 — Интерфейс запросов и редактирования

## Энциклопедия цивилизации

Версия: 0.1  
Класс: Implementation Specification  
Статус: рабочая нормативная спецификация  
Дата: 29 сентября 2026 года

---

## 1. Назначение

Документ определяет архитектуру интерфейса, через который человек или программный клиент получает доступ к Record, выполняет запросы и создаёт изменения.

Интерфейс является слоем над Storage Adapter.

    Query / Edit Interface
              ↓
       Storage Adapter
              ↓
            Backend

Интерфейс не является источником семантики и не должен скрыто изменять канонические Record.

## 2. Принципы

Интерфейс должен:

- явно различать чтение и изменение;
- сохранять Record identity и version;
- не скрывать неопределённость;
- не подменять исторические версии текущими;
- возвращать проверяемые ошибки;
- поддерживать read-only режим;
- быть заменяемым;
- не зависеть от конкретного UI.

Интерфейс не должен превращать удобство пользователя в скрытую семантическую трансформацию.

## 3. Query model

Запрос должен иметь явно определённые:

- условия;
- сортировку;
- ограничение количества;
- область поиска;
- версию данных, если она существенна;
- режим разрешения ссылок, если он используется.

Query не изменяет Record.

Нулевой результат означает отсутствие найденных записей по заданным условиям, а не доказательство отсутствия предмета.

## 4. Historical query

Должны поддерживаться запросы:

- текущего состояния;
- конкретной версии;
- диапазона версий;
- состояния на определённый момент, если такая семантика реализована.

Исторический запрос не должен автоматически разрешаться через текущую версию.

## 5. Edit model

Изменение должно проходить через:

    read current
        ↓
    verify expected version
        ↓
    construct new version
        ↓
    validate
        ↓
    persist
        ↓
    return new version

Редактор не должен напрямую изменять историческую версию.

## 6. Optimistic concurrency

Edit-запрос должен позволять указать ожидаемую версию.

Если фактическая версия отличается, результат:

    conflict

а не молчаливое объединение изменений.

Автоматическое merge допускается только при формально определённых правилах.

## 7. Validation boundary

До сохранения должны выполняться применимые структурные и типовые проверки.

Полная семантическая валидация может выполняться отдельным Validator.

Успешный edit не означает истинность содержания.

## 8. Unknown discipline

UI/API не должен преобразовывать:

- unknown;
- absent;
- not_applicable;
- not_observed;
- not_recorded

в одно значение только ради удобства отображения.

Если интерфейс использует упрощённое представление, исходное состояние должно сохраняться.

## 9. References

Редактор должен позволять различать:

- ссылку на Record;
- ссылку на конкретную Record version;
- неразрешённую ссылку.

Ссылка на Record без версии не должна автоматически означать ссылку на историческую версию.

## 10. Publication status

Интерфейс должен отдельно отображать publication_status.

Он не должен представлять его как оценку истинности.

Изменение publication_status является отдельным изменением Record и должно быть прослеживаемым.

## 11. Permissions

Минимально различаются права:

- read;
- create;
- edit;
- change_publication_status;
- archive;
- delete;
- administer.

Наличие права редактирования не означает право изменять нормативные Standards.

## 12. Audit

Изменения через интерфейс должны позволять установить:

- кто инициировал операцию;
- когда;
- над какой Record;
- над какой версией;
- какой результат получен;
- какая версия интерфейса использовалась.

Audit trail не заменяет Provenance содержания.

## 13. API independence

Интерфейс может быть:

- CLI;
- локальным GUI;
- web API;
- offline application;
- другим клиентом.

Все клиенты должны обращаться к одной определённой семантике операций.

UI не должен становиться единственным носителем правил.

## 14. Offline-first

Базовые операции чтения, проверки и редактирования должны быть реализуемы в локальной среде при наличии локального хранилища и необходимых Schema/Profile/Validator.

Сеть не должна быть обязательной для сохранения уже загруженного знания.

## 15. Ошибки

Минимально:

- not_found;
- version_not_found;
- conflict;
- invalid_record;
- validation_failed;
- permission_denied;
- read_only;
- storage_unavailable;
- unsupported_operation.

Ошибка интерфейса не должна маскироваться под отсутствие Record.

## 16. Security

Клиентские данные не должны автоматически исполняться.

Интерфейс должен:

- нормализовать вход;
- ограничивать ресурсы;
- защищать от path traversal;
- не доверять UI-полям как доказательству полномочий;
- не загружать внешние ресурсы без политики;
- сохранять границу между данными и кодом.

## 17. Tests

- Q01 — чтение Record;
- Q02 — чтение конкретной версии;
- Q03 — историческая версия не подменяется текущей;
- Q04 — создание Record;
- Q05 — update создаёт новую версию;
- Q06 — конфликт ожидаемой версии обнаруживается;
- Q07 — unknown state сохраняется;
- Q08 — reference version сохраняется;
- Q09 — publication_status не превращается в truth status;
- Q10 — read-only блокирует изменение;
- Q11 — permission denied не маскируется;
- Q12 — offline query работает без сети;
- Q13 — ошибка Storage не превращается в not_found;
- Q14 — audit trail создаётся;
- Q15 — повтор запроса даёт эквивалентный результат.

Стресс-тесты Q16–Q25:

- массовые запросы;
- большие результаты;
- сложные reference graph;
- большая история;
- конкурентные edits;
- большие Unicode-поля;
- повреждённый cache;
- недоступный Backend;
- ограниченные ресурсы;
- работа в read-only archive.

## 18. Инварианты

1. Query не изменяет Record.
2. Edit не изменяет историческую версию.
3. Историческая ссылка не перенаправляется текущей.
4. Conflict не скрывается.
5. Unknown не становится absent.
6. publication_status не является truth status.
7. UI не является источником нормативных правил.
8. Read-only действительно запрещает изменение.
9. Permission не определяется самим клиентом.
10. Интерфейс не зависит от конкретного Backend.

## 19. Критерии готовности

011 готов, если определены query model, edit model, historical access, concurrency, permissions, validation boundary, audit, offline operation, security, tests и invariants.

## 20. Статус

Документ определяет семантику интерфейсного слоя, но не конкретный протокол HTTP, UI framework или язык программирования.
