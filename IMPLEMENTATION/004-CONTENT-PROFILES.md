# 004 — Профили содержимого и первая схема

## Энциклопедия цивилизации

Версия: 0.1  
Статус: рабочий нормативный документ

---

## 1. Назначение

Этот документ определяет архитектуру специализированного Content для зарегистрированных типов Record и правила построения первой машиночитаемой схемы.

Он является следующим слоем после:

- FOUNDATION;
- STANDARD;
- IMPLEMENTATION/000-IMPLEMENTATION-MODEL;
- IMPLEMENTATION/001-RECORD-ENVELOPE;
- IMPLEMENTATION/002-SCHEMA-ARCHITECTURE;
- IMPLEMENTATION/003-TYPE-REGISTRY.

Главная задача:

```
Record Envelope
      +
Type Profile
      ↓
валидируемая Record
```

Этот документ не пытается сразу формализовать все 19 Standard до последнего поля.

Первая реализация должна быть минимальной, но не должна уничтожать смысл уже принятых стандартов.

---

## 2. Основное правило

Content не является второй Envelope.

Envelope отвечает за общую инфраструктурную семантику:

- идентичность;
- тип;
- версию;
- жизненный статус;
- происхождение;
- общие временные сведения;
- Scope;
- Context;
- Integrity.

Content отвечает за специализированный смысл конкретного типа.

Запрещается дублировать одно и то же значение в Envelope и Content без явно установленного правила источника истины.

---

## 3. Профиль типа

Для каждого зарегистрированного `record_type` существует нормативно описанный Type Profile. Его техническая реализация может быть полной или отложенной.

Минимальная структура профиля:

```
Type Profile
├── type_id
├── type_version
├── standard
├── implementation_status
├── content_schema
├── required_content
├── optional_content
├── references
├── semantic_constraints
└── migration_notes
```

Type Profile не является Record.

Он является метаданными реализации, описывающими, как валидировать Content данного типа.

---

## 4. Три уровня обязательности

Для каждого поля следует различать:

### 4.1. Structural required

Поле необходимо для технической структуры.

### 4.2. Semantic required

Поле необходимо для смысла данного типа по Standard.

### 4.3. Contextually required

Поле необходимо только при определённых условиях.

Например, временной интервал может быть необязателен для одной Record, но обязателен для конкретного утверждения, если без него меняется область применимости.

Эти уровни нельзя смешивать.

---

## 5. Неизвестное значение

Если Standard допускает неизвестность, Content Schema должна позволять её представить без выдумывания значения.

Предпочтительный принцип:

```
известное значение
или
структурированное значение неизвестности
```

а не:

```
произвольный null
```

Конкретная форма кодирования будет общей для Schema и должна быть определена до создания большого корпуса данных.

---

## 6. Первая реализация: базовый Content Contract

Первая схема должна установить общий контракт:

```
content:
  object
```

Content должен быть объектом, если соответствующий тип не требует иной формы и такое исключение явно обосновано.

Необходимо избегать универсального:

```
content: any
```

потому что это переносит всю семантику в свободный текст и лишает Validator возможности проверять структуру.

Одновременно нельзя превращать первую схему в полную онтологию мира.

---

## 7. Общий контракт идентификаторов

Идентификаторы, используемые в Content, должны быть структурно различимы по назначению.

Минимально:

```
record_id
version_id
referent_id
external_id
```

не следует смешивать в одно строковое поле без указания семантики.

Ссылка на Record должна иметь собственную структуру.

Минимальная форма:

```json
{
  "record_id": "…",
  "version": "…"
}
```

Если версия не указана, ссылка означает логическую Record, а не автоматически текущую версию.

---

## 8. Общий контракт времени

В Content нельзя использовать строку с произвольной датой как единственный способ выражения времени, если время имеет существенную семантику.

Общая модель должна позволять:

- точное время;
- дату;
- интервал;
- открытый интервал;
- приблизительное время;
- неизвестное время.

При этом:

```
created_at
≠
valid_time
≠
subject_time
```

---

## 9. Общий контракт Scope и Context

Content может ссылаться на отдельные Record типа `scope` и `context`, если соответствующий Standard это допускает.

Но Envelope `scope` и `context` не должны автоматически считаться Record типа `scope` и `context`.

Следует различать:

```
field in Envelope
≠
Record of type scope
```

Это особенно важно для первой JSON Schema.

---

## 10. Профили 001–019

Ниже фиксируется архитектурный минимум. Полные поля каждого Standard будут выведены из самих стандартов при построении Content Schema.

### 001 — record

Статус первой JSON Schema: `implemented`.

Назначение: базовая Record.

Content должен позволять представить специализированное содержимое только в случаях, когда специализированный профиль ещё не применяется.

Ограничение: `record` не должен использоваться для обхода обязательной типизации.

### 002 — claim

Статус первой JSON Schema: `implemented`.

Минимально должен позволять выразить:

- пропозициональное содержание;
- объект или референты, к которым оно относится, если это существенно;
- область применимости;
- необходимые ограничения.

Evidence Use не является частью Claim автоматически.

### 003 — source

Статус первой JSON Schema: `implemented`.

Минимально должен позволять описать:

- идентичность источника;
- происхождение;
- доступное содержимое или указатель на него;
- версию/издание, если применимо;
- ограничения доступности.

Source не равен Evidence Use.

### 004 — evidence_use

Статус первой JSON Schema: `implemented`.

Должен явно связывать:

- конкретный Claim;
- конкретный Source;
- материал или фрагмент источника;
- роль этого материала относительно Claim.

Evidence Use не превращается автоматически в Claim, Assessment или Inference.

### 005 — assessment

Статус первой JSON Schema: `implemented`.

Должен позволять представить:

- объект оценивания;
- оценочный конструкт;
- основание;
- результат оценки;
- неопределённость;
- ограничения;
- оценщика, если применимо.

Assessment не должен превращать оценку в неизменное свойство объекта.

### 006 — inference

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен позволять представить:

- исходные основания;
- полученный вывод;
- способ или правило вывода;
- ограничения;
- неопределённость.

Наличие Inference не означает автоматически правильность вывода.

### 007 — decision

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен позволять представить:

- субъект решения;
- рассматриваемую ситуацию;
- альтернативы, если они существенны;
- выбранный вариант;
- основания;
- Scope решения;
- ограничения.

Decision не равен Action.

### 008 — action

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен позволять представить:

- действие;
- исполнителя, если известен;
- объект действия;
- время;
- условия;
- связь с Decision, если она существует;
- факт исполнения отдельно от намерения и результата.

Action не равен Event и не равен Result.

### 009 — event

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен позволять представить:

- событие;
- временную характеристику;
- пространственную характеристику, если существенна;
- участников;
- наблюдаемую или зафиксированную характеристику события.

Event не должен автоматически означать причинность, намерение или ответственность.

### 010 — result

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен позволять представить результат в смысле соответствующего Standard.

Он не должен автоматически означать:

- полезный эффект;
- успех;
- причинённое изменение;
- положительный исход.

### 011 — state

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен позволять представить состояние относительно определённого носителя/референта и Scope/Context.

Historical State не должен автоматически становиться Current State.

### 012 — process

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен позволять представить процесс как структурированное содержание с:

- границами;
- стадиями или изменениями;
- условиями;
- участниками/объектами, если применимо;
- временной характеристикой.

Процесс не равен конкретному исполнению процедуры.

### 013 — relation

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен позволять представить:

- участников отношения;
- тип отношения;
- направление, если применимо;
- действительность во времени;
- Scope/Context, если существенны.

Relation не следует автоматически трактовать как самостоятельный предметный объект.

### 014 — identity

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен позволять представить утверждение или запись об идентичности/различении и основаниях такого вывода.

Идентификатор Record не является автоматически доказательством Identity.

### 015 — context

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен позволять структурно описывать условия, необходимые для интерпретации или применения содержания.

Context не должен автоматически становиться универсальным текущим контекстом пользователя.

### 016 — scope

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен позволять структурно задавать область применимости и её границы.

Scope не равен текущему значению по умолчанию.

### 017 — provenance

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен позволять представить происхождение, преобразования и линии происхождения.

Provenance не равен Authoring, Causality или Truth.

### 018 — authorship_contribution

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен различать:

- Author;
- Contribution;
- Participation;
- Credit;
- Provenance;
- Responsibility;
- Ownership;
- Rights.

Наличие аккаунта, устройства или обучающих данных не должно автоматически создавать соответствующее авторство или вклад.

### 019 — trust_reputation

Статус: `registered`; Content Schema будет добавлен в последующем вертикальном срезе.

Должен различать:

- Trust;
- Trust Assessment;
- Reputation;
- Reputation Signal;
- Evidence;
- Epistemic confidence.

Доверие и репутация не должны автоматически становиться доказательством истинности Claim.

## 11. Поля Envelope, которые не следует повторять в Content

Если значение уже является нормативным полем Envelope, Content не должен создавать вторую независимую копию без специального основания.

Особенно:

```
record_id
record_type
record_version
publication_status
schema

record_status
provenance
integrity
```

Если специализированный Standard требует ссылку на другую Record, это другая семантика и она должна быть представлена как структурная ссылка.

---

## 12. Discriminator

Для первой JSON Schema используется явный discriminator:

```
record_type
```

Validator должен выбирать Content Profile на основании этого значения.

Нельзя выбирать профиль по наличию определённых полей.

Пример запрещённой логики:

```
если есть "steps" → process
если есть "result" → result
```

---

## 13. Дополнительные поля

Первая Schema должна запрещать молчаливое появление неизвестных полей внутри критических структур там, где это способно скрыть ошибку.

Одновременно расширения должны иметь отдельный механизм.

Поэтому следует различать:

```
unknown field
≠
declared extension
```

Это позволяет обнаруживать опечатки и одновременно сохранять расширяемость.

---

## 14. Профиль и Standard

Type Profile не должен копировать весь текст Standard.

Standard остаётся нормативным источником семантики.

Profile переводит только те правила в технические ограничения, которые могут быть однозначно формализованы.

Пример:

```
Standard:
"Evidence Use связывает материал Source с Claim"
        ↓
Schema:
claim_ref + source_ref + material
```

Но:

```
Standard:
"Evidence Use не доказывает истину Claim"
```

не обязательно выражается структурным JSON Schema-ограничением.

Это становится правилом Semantic Validator.

---

## 15. Уровни будущей Schema

Предлагается разделить машиночитаемые схемы на:

### Envelope Schema

Проверяет общую Record.

### Content Schemas

Проверяют Content каждого типа.

### Reference Schemas

Проверяют форму структурных ссылок.

### Common Value Schemas

Проверяют общие конструкции:

- Time;
- Scope reference;
- Context reference;
- Provenance;
- Integrity;
- Unknown value.

### Semantic Validator

Проверяет правила, которые невозможно или нецелесообразно выразить только JSON Schema.

---

## 16. Первая JSON Schema

Первая JSON Schema должна начинаться с общего Envelope и discriminator.

Архитектурно:

```
Record
├── Envelope
│   ├── record_id
│   ├── record_type
│   ├── record_version
│   ├── record_status
│   ├── provenance
│   ├── created_at
│   ├── updated_at
│   ├── valid_time
│   ├── scope
│   ├── context
│   └── integrity
│
└── Content
    └── selected by record_type
```

Для первого вертикального среза допускается начать с профилей:

```
record
claim
source
evidence_use
assessment
```

а затем расширять покрытие до 019.

Но реестр типов должен оставаться полным.

---

## 17. Что JSON Schema не должна пытаться доказать

JSON Schema не может сама по себе доказать:

- истинность Claim;
- качество Evidence;
- правильность Inference;
- правильность Decision;
- успешность Action;
- причинность Event;
- истинность State;
- безопасность Procedure;
- надёжность Source;
- репутацию Agent;
- сохранение смысла после миграции.

Такие свойства требуют других уровней проверки.

---

## 18. Критерии готовности 004

Перед созданием машинного файла Schema необходимо проверить:

- все 19 типов имеют профиль;
- Envelope не дублируется Content;
- discriminator однозначен;
- ссылки имеют отдельную структуру;
- версии Record, Type и Schema разделены;
- unknown discipline сохранена;
- Scope и Context не смешаны;
- Provenance не смешивается с Authoring;
- Integrity не смешивается с Truth;
- Result и State не превращаются в новые Core Entities;
- неизвестные поля отличимы от объявленных расширений;
- структурные ограничения отделены от семантических;
- каждый технический constraint имеет нормативное основание.

## 19. Статус

Версия 0.1 является рабочей архитектурой Content Profiles.

Следующий этап:

```
004 Content Profiles
        ↓
005 JSON Schema
        ↓
006 Validator Architecture
```

Этот документ не изменяет семантику FOUNDATION или STANDARD.
