# 001 — Каноническая оболочка Record

## Энциклопедия цивилизации

Версия: 0.1  
Класс: Implementation Specification  
Статус: рабочая спецификация  
Дата: 29 сентября 2026 года

## 1. Назначение

Каноническая оболочка Record определяет минимальную общую структуру, необходимую для идентификации, версионирования, типизации, происхождения и безопасной обработки любой записи.

Она НЕ определяет специализированное содержимое Claim, Source, Assessment и других типов.

## 2. Минимальная структура

Каждая каноническая Record должна иметь:

- record_id
- record_type
- record_version
- type_version
- schema
- publication_status
- completion_status
- provenance

Дополнительные общие компоненты:

- content — если его использование предусмотрено Type Profile;
- created_at
- updated_at
- valid_time
- scope
- context
- integrity

Обязательность дополнительных компонентов определяется типом записи и соответствующим Standard. `content` не является универсально обязательным полем оболочки: содержательная структура определяется Type Profile.

## 3. record_id

`record_id` — устойчивый идентификатор логической идентичности Record.

Он не зависит от имени файла, URL, СУБД, языка публикации или конкретного представления.

Изменение Record не должно автоматически создавать новый record_id, если сохраняется её логическая идентичность.

## 4. record_type

`record_type` явно определяет специализированный тип записи.

Примеры: Record, Claim, Source, EvidenceUse, Assessment, Inference, Decision, Action, Event, Result, State, Process, Relation, Identity, Context, Scope, Provenance, AuthorshipContribution, TrustReputation.

Список типов не считается закрытым навсегда. Новый тип вводится по правилам расширения модели.

## 5. record_version

`record_version` идентифицирует конкретное состояние Record.

Минимально необходимо различать record_id и record_version.

Историческая ссылка должна иметь возможность однозначно определить конкретную версию. Предыдущие версии не уничтожаются из-за создания новой версии.

## 6. publication_status

Публикационный статус Record относится к её жизненному циклу и не определяет автоматически истинность содержания.

publication/lifecycle status ≠ epistemic assessment.

## 7. completion_status

`completion_status` описывает степень завершённости содержательного состояния Record и не является публикационным статусом, истинностью или эпистемической оценкой.

Базовые значения: `incomplete`, `partial`, `complete`, `unknown`, `not_applicable`.

`publication_status` и `completion_status` являются независимыми измерениями.

## 8. content

`content` содержит специализированное содержание Record.

Структура content определяется record_type и соответствующим Standard.

Оболочка не должна дублировать специализированные поля только ради удобства конкретного интерфейса.

## 9. provenance

Каждая Record должна позволять установить своё происхождение.

Минимальная семантика включает возможность указать создателя, время создания, основания или исходные записи, метод преобразования и соответствующую версию происхождения, когда это применимо.

Provenance не является доказательством истинности.

## 9. Time

Оболочка должна позволять различать created_at, updated_at и valid_time.

Техническое время изменения Record не является автоматически временем действительности содержания.

## 10. Scope и Context

Scope и Context могут быть представлены ссылками на соответствующие Record либо структурированными компонентами реализации.

Они не должны автоматически заполняться текущим пользовательским контекстом.

Отсутствие Scope или Context не означает универсальность содержания.

## 11. Integrity

`integrity` относится к технической целостности представления.

Она может включать алгоритм, digest, каноникализацию и подпись.

Техническая целостность не является эпистемической оценкой.

## 12. Ссылки

Ссылки на другие Record должны быть структурированными и, когда историческая точность этого требует, указывать конкретную версию.

Неразрешённая ссылка не должна молча превращаться в ссылку на текущую версию.

## 13. Unknown discipline

Каноническая оболочка должна позволять различать как минимум: unknown, absent, not_applicable, not_observed, not_recorded.

Конкретная машиночитаемая кодировка будет определена Schema.

Простой null не должен получать несколько несовместимых семантик без явного правила.

## 14. Каноническое представление

Каноническое представление Record должно быть детерминированным настолько, насколько это необходимо для хеширования, сравнения, проверки целостности и воспроизводимого экспорта.

Порядок полей и формат сериализации не должны менять семантику Record.

## 15. Запрещённые сокращения

- filename = record_id
- database primary key = canonical identity
- published = true → true
- valid = true → epistemically established
- hash valid → content true
- missing → absent

Эти равенства запрещены как универсальные семантические преобразования.

## 16. Критерий перехода к Schema

Record Envelope может перейти к машинной Schema после проверки совместимости с Record Standard, Identity, Version, Provenance, Scope, Context и Integrity; отсутствия скрытой семантики; и возможности сериализации без потери смысла.
