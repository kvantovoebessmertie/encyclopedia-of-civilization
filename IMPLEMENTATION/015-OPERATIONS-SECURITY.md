# 015 — Эксплуатация и безопасность

## Энциклопедия цивилизации

Версия: 0.1  
Класс: Implementation Specification  
Статус: рабочая нормативная спецификация  
Дата: 29 сентября 2026 года

---

## 1. Назначение

Документ определяет эксплуатационные требования для долговременной системы: резервирование, контроль целостности, управление доступом, обновления, наблюдаемость и безопасное восстановление.

## 2. Принципы

Эксплуатация не должна менять каноническую семантику.

Основные принципы:

- минимальные полномочия;
- проверяемость;
- обратимость;
- независимые копии;
- offline recovery;
- явные версии;
- отсутствие скрытых преобразований.

## 3. Backups

Должны существовать:

- регулярные резервные копии;
- независимая копия;
- Portable Package;
- периодическая проверка восстановления.

Backup не заменяет Portable Package.

## 4. Integrity checks

Периодически проверяются:

- Record;
- package;
- Schema;
- Profiles;
- Standards;
- Validator;
- migration artifacts.

Нарушение integrity фиксируется как технический инцидент.

## 5. Access control

Минимально различаются:

- reader;
- editor;
- validator operator;
- publisher;
- administrator.

Роль не является доказательством компетенции в предметной области.

## 6. Separation of duties

Критические операции желательно разделять:

- изменение Standards;
- изменение Schema;
- публикацию;
- административные изменения;
- восстановление;
- удаление.

Один технический оператор не должен автоматически получать все полномочия.

## 7. Change management

Изменения должны иметь:

- идентификатор;
- причину;
- описание;
- затронутые компоненты;
- версию;
- тесты;
- rollback plan, если применимо.

Архитектурные изменения должны оформляться через ADR по правилам проекта.

## 8. Dependency management

Зависимости должны быть:

- перечислены;
- версионированы;
- проверяемы;
- воспроизводимо устанавливаемы, если это возможно;
- заменяемы при необходимости.

Не следует полагаться на плавающие версии для архивной сборки.

## 9. Secrets

Секреты не должны храниться:

- в Record;
- в Portable Package;
- в Fixtures;
- в публичных логах;
- в исходном коде.

Секреты эксплуатации должны быть отделены от канонических данных.

## 10. Logging

Логи должны фиксировать технические операции, но не должны незаметно становиться вторичным источником семантики.

Минимально:

- время;
- компонент;
- операция;
- субъект;
- результат;
- error code;
- версия компонента.

## 11. Incident handling

Для инцидента должны сохраняться:

- время;
- затронутый компонент;
- техническая причина, если установлена;
- затронутые версии;
- последствия;
- действия восстановления;
- итог проверки.

Технический инцидент не должен автоматически трактоваться как ложность предметного содержания.

## 12. Update strategy

Обновление должно:

1. проверить совместимость;
2. создать backup/package;
3. выполнить тесты;
4. применить изменение;
5. проверить integrity;
6. проверить Validator;
7. проверить recovery.

Для несовместимого изменения применяется Migration.

## 13. Rollback

Rollback не должен уничтожать уже сохранённую историю.

Если rollback физического Backend невозможен без потери истории, предпочтительнее восстановление из Portable Package.

## 14. Security boundaries

Нужно защищать:

- import;
- export;
- package extraction;
- file paths;
- external links;
- credentials;
- APIs;
- admin operations;
- recovery environment.

Недоверенные данные должны считаться данными, а не инструкциями.

## 15. Supply-chain security

Для инструментов и зависимостей рекомендуется фиксировать:

- версию;
- источник;
- digest;
- дату получения;
- применимость.

Необходимо различать целостность инструмента и доверие к его результату.

## 16. Disaster recovery

Периодически выполняется recovery drill:

    backup/package
        ↓
    clean environment
        ↓
    integrity
        ↓
    validation
        ↓
    storage restore
        ↓
    publication
        ↓
    report

## 17. Tests

- O01 — backup создаётся;
- O02 — package проходит integrity;
- O03 — восстановление проходит;
- O04 — неавторизованный edit блокируется;
- O05 — read-only archive защищён;
- O06 — секреты не попадают в package;
- O07 — dependency versions фиксированы;
- O08 — rollback не уничтожает историю;
- O09 — повреждение обнаруживается;
- O10 — recovery drill успешен.

Стресс-тесты O11–O20:

- отказ Backend;
- потеря индекса;
- потеря узла;
- повреждение package;
- компрометация dependency;
- массовый import;
- массовый export;
- длительное offline хранение;
- большой архив;
- повторный recovery drill.

## 18. Invariants

1. Backup не равен Package.
2. Integrity не равна truth.
3. Секреты не входят в канонические данные.
4. Rollback не уничтожает историю.
5. Migration не скрывается в update.
6. Недоверенные данные не исполняются.
7. Роли доступа не являются эпистемической оценкой.
8. Recovery должен быть проверяемым.

## 19. Критерии готовности

015 готов, если определены backup, integrity, access, change management, dependencies, secrets, logging, incident handling, update, rollback, disaster recovery и tests.

## 20. Статус

Документ определяет эксплуатационные требования и не является конкретной инструкцией администрирования отдельной СУБД.
