# 010 — Адаптер хранения

## Энциклопедия цивилизации

Версия: 0.1  
Класс: Implementation Specification  
Статус: рабочая нормативная спецификация  
Дата: 29 сентября 2026 года

---

## 1. Назначение

Настоящий документ определяет архитектуру Storage Adapter — заменяемого слоя между канонической моделью Record и конкретным физическим хранилищем.

Адаптер должен позволять сохранять, читать, находить и восстанавливать Record без переноса семантики Энциклопедии в конкретную СУБД, файловую систему, облако или другой механизм хранения.

Главный принцип:

> **Хранилище предоставляет механизм сохранения и доступа, но не определяет смысл Record.**

---

## 2. Место в архитектуре

Storage Adapter является следующим слоем после Portable Package:

    Canonical Records
          ↓
       Schema
          ↓
      Validator
          ↓
   Portable Package
          ↓
   Storage Adapter
          ↓
   Query / Edit Interface
          ↓
   Publication Builder

Storage Adapter не должен становиться источником нормативной семантики.

Если физическое хранилище не способно непосредственно представить некоторую семантику, адаптер обязан использовать определённое представление или сообщить о невозможности операции, а не молча отбросить значение.

---

## 3. Граница ответственности

Storage Adapter отвечает за:

- сохранение Record;
- чтение Record;
- поиск по явно определённым индексируемым свойствам;
- получение конкретной версии;
- перечисление доступных версий;
- обнаружение отсутствующих данных;
- сохранение технической целостности хранения;
- атомарность поддерживаемых операций;
- экспорт и импорт через Portable Package;
- сообщение об ограничениях конкретного Backend.

Storage Adapter не отвечает за:

- установление истинности Claim;
- оценку качества Evidence;
- принятие Decision;
- интерпретацию текста вместо Type Profile;
- изменение Standard;
- скрытую миграцию семантики;
- публикационное оформление.

---

## 4. Storage Backend

Backend — конкретный механизм физического хранения.

Допустимые реализации могут включать:

- файловую систему;
- embedded database;
- серверную СУБД;
- object storage;
- другой совместимый механизм.

Выбор Backend не должен менять каноническую модель.

Минимальная архитектура:

    Canonical Model
          ↓
    Storage Adapter API
          ↓
    Backend

Один и тот же набор Record должен быть переносим между совместимыми Backend без изменения их семантики.

---

## 5. Каноническая единица хранения

Основной единицей хранения является Record Version.

При этом:

    record_id
        =
    логическая идентичность Record

    record_version
        =
    конкретная версия Record

Backend не должен использовать физический адрес объекта как замену record_id.

Например:

- путь файла;
- database primary key;
- внутренний идентификатор объекта;
- URL объекта

могут быть техническими идентификаторами Backend, но не являются автоматически канонической идентичностью Record.

---

## 6. Необходимые операции

Минимальный интерфейс адаптера должен концептуально поддерживать:

- create;
- read;
- read_version;
- list_versions;
- update;
- delete;
- restore;
- exists;
- query;
- export;
- import;
- validate_storage_state.

Конкретные имена API могут отличаться.

Семантика операций должна быть определена независимо от языка программирования.

---

## 7. Create и Update

create создаёт новую Record.

Операция должна проверять как минимум:

- уникальность record_id;
- допустимость record_type;
- наличие версии;
- применимость Type Profile;
- структурную целостность;
- обязательные поля;
- правила версии.

Если Record с таким record_id уже существует, операция не должна молча перезаписывать существующую историю.

Изменение существующей Record должно создавать новую record_version, если изменение является семантически версионным.

Предыдущая версия должна сохраняться, если Standard или политика хранения не определяют иной явно зафиксированный режим.

    Record v1
       ↓ update
    Record v2

не должно превращаться в уничтожение v1.

---

## 8. Delete и Archive

Удаление физического объекта и прекращение использования Record — разные понятия.

publication_status = archived не означает физическое удаление.

Storage Adapter не должен превращать:

- withdrawn;
- archived;
- недоступную запись;
- физически удалённую запись

в одно состояние.

Если физическое удаление разрешено политикой хранения, оно должно быть обнаружимо и не должно маскироваться под сохранённую историческую версию.

Для долговременного архива предпочтительно логическое сохранение Record.

---

## 9. Version retrieval

Адаптер должен поддерживать явное получение конкретной версии:

    read_version(record_id, record_version)

Запрос без версии может означать текущую версию только если это явно определено API.

Система не должна молча разрешать историческую ссылку на текущую версию.

Если требуемая версия отсутствует, результат должен содержать определённое состояние ошибки или неполноты.

---

## 10. References

Storage Adapter должен сохранять ссылки между Record без изменения их семантики.

Минимально должны сохраняться:

- целевой record_id;
- record_version, если ссылка версионная;
- тип связи, если он задан;
- состояние разрешения ссылки.

Неразрешённая ссылка не должна автоматически преобразовываться в ссылку на текущую версию.

Проверка ссылочной целостности выполняется Validator-слоем.

---

## 11. Provenance, Time, Scope и Context

Storage Adapter должен сохранять Provenance как часть Record.

Технические события хранения могут иметь собственную provenance:

- кто импортировал Record;
- когда выполнен импорт;
- какой Backend использовался;
- каким адаптером выполнена операция;
- какая версия инструмента использовалась.

Техническая provenance операции хранения не заменяет provenance самого знания.

Backend timestamps не должны автоматически интерпретироваться как время события, наблюдения или действительности содержания.

Семантически значимые временные поля Record должны храниться отдельно от технических timestamps Backend.

Scope и Context также должны сохраняться без скрытого заполнения текущими:

- пользователем;
- сервером;
- геолокацией;
- временем;
- Backend metadata.

---

## 12. Unknown states

Адаптер не должен превращать неизвестность в отсутствие значения.

Как минимум должны быть различимы:

- unknown;
- absent;
- not_applicable;
- not_observed;
- not_recorded.

Конкретная машинная кодировка определяется Schema и Type Profile.

Если Backend не поддерживает необходимое различие напрямую, адаптер обязан использовать lossless representation либо сообщить о несовместимости.

---

## 13. Integrity

Storage Adapter должен поддерживать проверяемую техническую целостность там, где она предусмотрена архитектурой.

Могут использоваться:

- digest;
- checksum;
- content-addressed storage;
- transaction integrity;
- immutable object metadata.

Но:

    storage integrity
        ≠
    epistemic truth

Успешное чтение объекта не означает истинность его содержимого.

Изменение Record, обнаруженное механизмом integrity, должно сообщаться как техническое нарушение, а не автоматически как ложность Claim.

---

## 14. Atomicity и Transactions

Операции, изменяющие несколько взаимозависимых объектов, должны быть атомарными там, где Backend это поддерживает.

Если полная атомарность невозможна, адаптер обязан:

- определить границу операции;
- сообщить о частичном результате;
- не выдавать частичный результат за полный;
- обеспечить последующую проверку состояния.

Transaction — технический механизм Backend.

Commit транзакции не означает истинность данных, публикацию, утверждение Claim или успешность действия в реальном мире.

---

## 15. Concurrency

При одновременной работе нескольких процессов адаптер должен предотвращать незаметное уничтожение изменений.

Минимально должны быть предусмотрены:

- обнаружение конфликта версии;
- optimistic concurrency либо эквивалентный механизм;
- проверка ожидаемой версии перед update;
- детерминированное сообщение о конфликте.

Автоматическое разрешение конфликта не должно изменять семантику Record без явно определённого правила.

---

## 16. Idempotency

Операции импорта и восстановления должны иметь определённую семантику повторного запуска.

Повтор операции не должен создавать незапланированные дубликаты Record.

Особенно важно обеспечить идемпотентность для:

- Portable Package import;
- recovery;
- migration;
- batch operations.

Если операция не является идемпотентной, это должно быть явно указано.

---

## 17. Query и индексы

Query должен возвращать Record или их идентификаторы по явно определённым условиям.

Query не должен:

- скрыто менять Record;
- создавать новые Record;
- изменять publication_status;
- превращать отсутствие результата в доказательство отсутствия сущности.

Результат zero records означает отсутствие найденных записей по условиям запроса, а не автоматически отсутствие сущности.

Индексы являются производным техническим механизмом.

Повреждение или устаревание индекса не должно уничтожать канонические данные.

---

## 18. Cache

Cache не является каноническим хранилищем.

Кэшированная Record должна иметь возможность проверки соответствия канонической версии.

Устаревший cache не должен молча заменять новую Record.

Если cache недоступен, система не должна создавать ложного впечатления, что канонические данные отсутствуют.

---

## 19. Portable Package integration

Storage Adapter должен обеспечивать экспорт в Portable Package и импорт из него.

Экспорт должен сохранять:

- identity;
- versions;
- type/profile information;
- provenance;
- references;
- relevant time;
- Scope;
- Context;
- uncertainty;
- integrity metadata.

Импорт не должен молча:

- менять record_id;
- сворачивать историю;
- заменять исторические ссылки текущими;
- удалять неизвестность;
- менять publication_status;
- менять семантику Type Profile.

---

## 20. Backup и Recovery

Резервная копия Backend не является автоматически Portable Package.

Backup может зависеть от конкретной СУБД, версии Backend, операционной системы и конфигурации.

Для долговременной независимости должен существовать путь:

    Backend
       ↓
    Portable Package
       ↓
    clean environment
       ↓
    Storage Adapter
       ↓
    restored Records

Recovery должен быть проверяемым независимо от исходного Backend, если пакет заявлен как self-contained.

---

## 21. Backend capability model

Каждый Adapter должен явно описывать возможности Backend.

Минимальный набор capability:

- versioned_records;
- immutable_history;
- transactions;
- atomic_batch;
- concurrent_updates;
- reference_indexing;
- integrity_verification;
- package_import;
- package_export;
- offline_operation.

Отсутствие capability не должно маскироваться под её наличие.

Если функция реализуется самим Adapter поверх Backend, это должно быть явно документировано.

---

## 22. Ошибки и состояния

Адаптер должен различать как минимум:

- not_found;
- version_not_found;
- conflict;
- invalid_record;
- unsupported_type;
- integrity_failure;
- dependency_missing;
- storage_unavailable;
- transaction_failed;
- partial_result;
- unsupported_operation.

Ошибка Backend не должна автоматически интерпретироваться как отсутствие Record.

Например:

    storage_unavailable
        ≠
    record_not_found

---

## 23. Read-only режим

Adapter должен поддерживать read-only режим для:

- архивов;
- исторических пакетов;
- recovery;
- независимой проверки.

В read-only режиме операции изменения не должны выполняться даже если Backend технически позволяет запись.

---

## 24. Security

Storage Adapter должен рассматриваться как граница безопасности.

Он не должен:

- выполнять содержимое Record как код;
- доверять имени файла как идентичности;
- допускать path traversal;
- принимать произвольные пути без нормализации;
- автоматически загружать внешние ресурсы;
- выполнять скрипты из Portable Package;
- считать данные безопасными только потому, что они прошли Schema validation.

Доступ к Backend должен следовать принципу минимально необходимых полномочий.

---

## 25. Data loss policy

Любая операция, потенциально приводящая к потере семантически значимых данных, должна иметь явно определённую политику.

Нельзя молча терять:

- исторические версии;
- ссылки;
- provenance;
- Scope;
- Context;
- uncertainty;
- publication_status;
- type/profile information.

Если Backend не поддерживает необходимое представление, операция должна завершаться ошибкой либо явно маркироваться как lossy по правилам Migration.

---

## 26. Migration boundary

Storage Adapter не должен самовольно изменять Schema или Type Profile при чтении.

Миграция является отдельным управляемым процессом, определённым в 008-VERSIONING-MIGRATION.md.

Разделение:

    Storage Adapter
        =
    сохранение / получение

    Migration
        =
    контролируемое преобразование

Это предотвращает скрытое изменение исторического представления при обычном чтении.

---

## 27. Determinism и Audit trail

При одинаковом состоянии Backend, одинаковой версии Adapter и одинаковом запросе результат должен быть эквивалентным.

Если порядок результатов не является частью семантики, он должен быть явно определён как незначимый либо детерминированный по установленному правилу.

Для критических операций рекомендуется сохранять технический журнал:

- время;
- операцию;
- субъект операции;
- Record identity;
- версию;
- результат;
- причину ошибки;
- версию Adapter.

Audit trail не заменяет Provenance Record и не является доказательством истинности содержания.

## 28. Тесты

Минимальный набор:

- S01 — создание новой Record;
- S02 — повторное создание того же record_id обнаруживает конфликт;
- S03 — update сохраняет предыдущую версию;
- S04 — чтение конкретной версии возвращает именно её;
- S05 — отсутствующая версия не подменяется текущей;
- S06 — неизвестная ссылка не превращается в текущую;
- S07 — publication_status не меняется при обычном чтении;
- S08 — Provenance сохраняется при round-trip;
- S09 — Scope и Context сохраняются;
- S10 — unknown state сохраняется;
- S11 — integrity failure обнаруживается;
- S12 — storage unavailable не маскируется как not_found;
- S13 — concurrent update обнаруживает конфликт;
- S14 — повторный import не создаёт незапланированные дубликаты;
- S15 — read-only режим блокирует изменение;

## 29. Инварианты

1. Backend не является источником семантики Record.
2. Физический адрес не является автоматически record_id.
3. record_id не равен record_version.
4. Update не должен молча уничтожать историю.
5. Историческая версия не заменяется текущей.
6. Ошибка Backend не равна not_found.
7. publication_status не является truth status.
8. Provenance хранения не заменяет Provenance знания.
9. Integrity не равна truth.
10. Cache не является каноническим источником.
11. Query не изменяет Record.
12. Migration не выполняется скрыто при обычном чтении.
13. Unknown не превращается в absent.
14. Lossy operation не маскируется под lossless.
15. Read-only режим не должен изменять данные.
16. Portable Package остаётся независимым от конкретного Backend.
17. Storage Adapter не принимает эпистемические решения за Validator.
18. Индекс не является единственным хранилищем канонического значения.

## 32. Критерии готовности

010 считается готовым, если:

- определена граница Storage Adapter;
- Backend отделён от канонической модели;
- определены базовые операции;
- разделены create/update/delete/archive;
- сохранена историчность;
- поддерживается получение конкретной версии;
- ссылки не подменяются текущими версиями;
- сохранены Provenance, Scope, Context и uncertainty;
- определены integrity и atomicity;
- определены concurrency и idempotency;
- определён Query без скрытой семантики;
- определена интеграция с Portable Package;
- Migration отделена от обычного хранения;
