# 000 — Модель реализации

## Энциклопедия цивилизации

Версия: 0.1  
Класс: Implementation Specification  
Статус: рабочая спецификация  
Дата: 29 сентября 2026 года

---

## 1. Назначение

Настоящий документ определяет связующий слой между фундаментальной архитектурой проекта, нормативными стандартами и будущей технической реализацией.

Он отвечает на вопрос:

> Как превратить семантическую модель Энциклопедии в устойчивую машиночитаемую систему, не изменив её смысл?

Документ не является схемой конкретной базы данных и не привязывает проект к конкретной СУБД, языку программирования, веб-платформе или поставщику инфраструктуры.

---

## 2. Нормативная иерархия

Реализация должна следовать следующему порядку зависимости:

```
FOUNDATION
    ↓
STANDARD
    ↓
IMPLEMENTATION MODEL
    ↓
MACHINE-READABLE SCHEMA
    ↓
VALIDATORS
    ↓
STORAGE / SERVICES / TOOLS
    ↓
PUBLICATIONS
```

Техническая реализация НЕ ДОЛЖНА молча изменять семантику Foundation или Standard.

Если реализация обнаруживает противоречие с нормативной моделью, это является архитектурным вопросом, а не основанием для неявного изменения смысла.

---

## 3. Канонический объект хранения

Каноническим объектом реализации является `Record`.

Каждая Record ДОЛЖНА иметь:

- устойчивый идентификатор;
- тип;
- версию;
- содержимое, соответствующее типу;
- состояние публикационного жизненного цикла;
- происхождение;
- возможность определить применимый Scope и Context, когда они релевантны;
- историю версий.

Технический формат записи является представлением Record и НЕ ЯВЛЯЕТСЯ её идентичностью.

Путь файла, URL, строка базы данных или внутренний database key НЕ ДОЛЖНЫ использоваться как единственный устойчивый идентификатор.

---

## 4. Identity и Version

Идентификатор и версия должны быть разделены.

```
record_id
    ≠
version_id
```

Изменение, которое создаёт новую семантическую версию Record, НЕ ДОЛЖНО уничтожать предыдущую версию.

Система должна позволять однозначно ссылаться как на:

- логическую идентичность Record;
- конкретную версию Record.

Ссылки, для которых важна историческая точность, ДОЛЖНЫ иметь возможность указывать конкретную версию.

---

## 5. Типизация

Каждая Record ДОЛЖНА иметь явно определённый тип.

Пример:

```text
record.type = Claim
record.type = Source
record.type = Assessment
record.type = Event
...
```

Тип не должен определяться только по:

- имени файла;
- расположению;
- заголовку Markdown;
- свободному тексту.

Машинная схема должна обеспечивать проверяемое соответствие типа структуре записи.

---

## 6. Содержимое и семантическая роль

Тип записи определяет допустимую семантику содержимого.

Система НЕ ДОЛЖНА автоматически выводить семантическую роль только из текстового совпадения.

Например:

```
Source
    ≠
Evidence Use
    ≠
Claim
    ≠
Assessment
    ≠
Inference
```

Связь между ними должна быть представлена структурированно и проверяемо.

---

## 7. Ссылки между записями

Связи между Record ДОЛЖНЫ ссылаться на устойчивые идентификаторы.

Если для корректной исторической интерпретации важна версия, ссылка ДОЛЖНА указывать на конкретную версию.

Недействительная ссылка НЕ ДОЛЖНА молча интерпретироваться как:

- отсутствующая запись;
- неизвестная запись;
- новая версия;
- текущая версия.

Неразрешённая ссылка должна иметь явно определённое техническое состояние.

---

## 8. Время

Реализация должна различать как минимум:

- время создания записи;
- время изменения записи;
- время действительности содержания, если применимо;
- время события/наблюдения/деятельности, если применимо.

Техническое время изменения записи НЕ ДОЛЖНО автоматически интерпретироваться как время, к которому относится содержание.

---

## 9. Scope и Context

Scope и Context являются структурированными механизмами ограничения применимости.

Реализация НЕ ДОЛЖНА считать две записи взаимозаменяемыми только потому, что их содержание текстово совпадает.

Совместимость должна учитывать релевантные:

- временные ограничения;
- пространственные ограничения;
- популяцию;
- условия;
- технологическую среду;
- масштаб;
- уровень подготовки;
- другие явно заданные ограничения.

Если совместимость неизвестна, система должна сохранять состояние неизвестности, а не автоматически считать записи совместимыми.

---

## 10. Provenance

Происхождение должно быть машиночитаемым.

Минимально необходимо сохранять возможность установить:

- происхождение Record;
- автора/участников, когда они известны;
- основания создания;
- использованные источники или входные записи;
- преобразования;
- версию происхождения.

Provenance НЕ ДОЛЖЕН автоматически интерпретироваться как доказательство истинности содержания.

---

## 11. Эпистемическая семантика

Техническая система должна сохранять различия:

```
Source
→ Evidence Use
→ Claim
→ Assessment
→ Inference
```

и

```
Inference
→ Decision
→ Action
→ Event
→ Result
→ State
```

Наличие связи между двумя Record НЕ означает автоматически:

- причинность;
- истинность;
- успешность;
- одобрение;
- юридическую ответственность;
- авторство.

Такие свойства должны быть представлены только при наличии соответствующей семантики и оснований.

---

## 12. Unknown ≠ Absent

Модель реализации обязана иметь способ отличать как минимум:

- значение отсутствует;
- значение неизвестно;
- значение неприменимо;
- значение не наблюдалось;
- значение не было записано;
- значение действительно отсутствует.

Один технический `null` НЕ ДОЛЖЕН автоматически использоваться как универсальный смысл всех этих состояний.

Конкретная кодировка будет определена машинной схемой.

---

## 13. Историчность

Исторические версии должны быть сохраняемыми.

Система НЕ ДОЛЖНА:

- молча переписывать исторические записи;
- заменять исторический State текущим State;
- изменять историческую Evidence Use из-за изменения Source;
- переносить историческую Assessment на новую версию Target;
- заменять исторический Context современным Context.

Текущая нормализация данных НЕ ДОЛЖНА уничтожать историческую семантику.

---

## 14. Integrity

Техническая целостность и эпистемическая достоверность различаются.

Проверка:

```
hash valid
```

может установить целостность данных относительно проверяемого представления, но НЕ устанавливает истинность содержания.

Система должна иметь отдельные механизмы для:

- структурной валидности;
- ссылочной целостности;
- версионной целостности;
- криптографической целостности;
- эпистемической оценки.

---

## 15. Storage independence

Каноническая модель НЕ ДОЛЖНА зависеть от конкретной СУБД.

Должна существовать возможность экспортировать канонические записи в переносимый формат без потери:

- идентичности;
- версии;
- ссылок;
- происхождения;
- временной семантики;
- Scope;
- Context;
- статусов;
- неопределённости.

СУБД является механизмом реализации, а не каноническим источником смысла.

---

## 16. Publication independence

Публикация является производным представлением.

Изменение:

- сайта;
- PDF;
- интерфейса;
- печатного тома;
- языка;
- формата экспорта

НЕ ДОЛЖНО само по себе изменять каноническую Record.

Публикация должна иметь возможность ссылаться на конкретные версии исходных записей.

---

## 17. Validator как обязательный слой

Любая нормативная машиночитаемая реализация должна иметь автоматическую проверку.

Минимальные классы проверок:

1. структурная валидность;
2. типизация;
3. обязательные поля;
4. ссылки;
5. версии;
6. Scope/Context;
7. Provenance;
8. историческая целостность;
9. запрещённые семантические скачки;
10. согласованность с Foundation и Standard.

Validator НЕ ДОЛЖЕН выдавать «истина» только на основании прохождения технической проверки.

---

## 18. Canonical package

Проект должен иметь канонический переносимый пакет данных.

Пакет должен включать:

- данные;
- схему;
- версии схем;
- манифест;
- информацию о целостности;
- инструкции восстановления;
- информацию о версии программных инструментов, если она необходима;
- сведения о совместимости.

Пакет должен быть пригоден для независимого копирования и проверки.

---

## 19. Recovery requirement

Долговременная система считается технически пригодной к архивированию только если её можно восстановить из сохранённого набора материалов без доступа к исходному серверу.

Recovery test должен проверять:

```
archive
→ integrity check
→ schema acquisition
→ tool acquisition
→ data import
→ validation
→ publication/build
```

Результат восстановления должен быть проверяемым.

---

## 20. Compatibility

Изменение схемы НЕ ДОЛЖНО молча ломать существующие записи.

Для несовместимых изменений должны существовать:

- новая версия схемы;
- правила миграции;
- описание несовместимости;
- тесты миграции;
- возможность сохранить исходное представление.

---

## 21. Запрет скрытой семантики

Если значение необходимо для правильной интерпретации записи, оно НЕ ДОЛЖНО храниться только в:

- названии файла;
- порядке строк;
- визуальном оформлении;
- комментарии;
- человеческой договорённости;
- конкретном интерфейсе.

Существенная семантика должна быть представлена структурированно.

---

## 22. Минимальная архитектура реализации

Первая рабочая реализация должна содержать:

```
Canonical Records
        ↓
Schema
        ↓
Validator
        ↓
Portable Package
        ↓
Storage Adapter
        ↓
Query / Edit Interface
        ↓
Publication Builder
```

Компоненты должны быть заменяемыми.

---

## 23. Порядок дальнейшей реализации

Следующий порядок является обязательным для первого прототипа:

1. зафиксировать Implementation Model;
2. определить минимальный канонический Record Envelope;
3. определить машинную схему;
4. создать validator;
5. создать набор тестовых Record;
6. проверить миграции и версии;
7. создать portable package;
8. создать минимальный storage adapter;
9. создать простой интерфейс редактирования/запроса;
10. собрать первую публикацию;
11. провести recovery test.

---

## 24. Критерий готовности Implementation Model

Implementation Model считается пригодной для перехода к Schema, если:

- она не противоречит Foundation;
- она не переопределяет Standard;
- все обязательные сквозные механизмы представлены;
- историчность сохраняется;
- неизвестность не теряется;
- хранилище и публикация разделены;
- техническая целостность не смешивается с истинностью;
- существует определённый путь к validator;
- существует определённый путь к portable package;
- не требуется конкретная платформа для сохранения смысла.

---

## 25. Статус

На момент версии 0.1 настоящая спецификация является рабочей.

Она не объявляет техническую реализацию завершённой.

Следующий обязательный артефакт:

```
IMPLEMENTATION/001-RECORD-ENVELOPE.md
```

Он должен определить минимальную машиночитаемую оболочку Record, не подменяя специализированные стандарты содержательной схемой.
