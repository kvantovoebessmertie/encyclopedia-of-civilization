# 008 — Версионирование и миграция

## Энциклопедия цивилизации

Версия: 0.1  
Класс: Implementation Specification  
Статус: рабочая нормативная спецификация  
Дата: 29 сентября 2026 года

---

## 1. Назначение

Этот документ определяет правила технического версионирования Record, Schema, Type Profile, Standard, Validator и миграций.

Главная цель:

> **Изменение технического представления не должно незаметно переписывать исторический смысл.**

## 2. Версионные сущности

Нужно различать:

    record_id
    record_version
    type_version
    schema_version
    standard_version
    validator_version
    validator_rule_set_version
    migration_version
    package_version

Они имеют разные функции.

## 3. Record version

record_id идентифицирует логическую Record.

record_version идентифицирует конкретное историческое состояние.

Создание новой семантически значимой версии означает:

    same record_id
    + new record_version

Старая версия должна оставаться разрешимой согласно политике хранения.

## 4. Что создаёт новую Record version

Новая версия требуется при изменении семантически значимого состояния.

Примеры:

- изменён Claim;
- изменён Source;
- изменён Scope;
- изменён Context;
- изменено существенно значимое provenance;
- изменён результат Assessment;
- изменён нормативно значимый publication state, если история требует его сохранения.

Техническое изменение, не меняющее канонический смысл, может быть миграцией представления без новой Record version, если это явно определено.

## 5. Исправление не должно скрывать новую семантику

Техническое исправление может быть:

- новой Record version;
- миграцией представления;
- отдельным repair artifact.

Выбор зависит от того, меняется ли канонический смысл.

Запрещено скрывать новое содержание под видом технического исправления.

## 6. Историческая неизменяемость

После публикации историческая версия не должна молча переписываться.

Допустимы:

- новая версия;
- provenance correction;
- ссылка на correction;
- migration metadata;
- изменение физического представления без изменения канонического смысла.

Недопустимо менять старую версию так, чтобы её историческое содержание стало другим.

## 7. Version graph

История может быть графом:

    Record
      │
      ├── v1
      ├── v2
      └── v3

Если branching разрешён:

    v1
    ├── v2a
    └── v2b

Политика проекта должна явно определить допустимость ветвления.

Validator не должен выбирать ветвь автоматически без нормативного правила.

## 8. Type Profile version

type_version относится к семантическому профилю типа.

Изменение Type Profile может:

- расширить допустимые данные;
- изменить структурные ограничения;
- изменить семантические требования;
- потребовать миграции.

Новая версия Type Profile не создаёт автоматически новую версию каждой Record.

## 9. Schema version

schema_version относится к машиночитаемой схеме.

Изменение Schema может быть:

- совместимым;
- условно совместимым;
- несовместимым.

Schema version не является Record version.

## 10. Standard version

Изменение Standard является нормативным изменением и не должно маскироваться под изменение Schema.

Если новая версия Standard меняет семантику, необходимо определить:

- дату или момент вступления;
- применимость;
- совместимость;
- необходимость миграции;
- историческое действие.

## 11. Validator version

Изменение алгоритма Validator может менять ValidationResult при неизменных Record.

Поэтому Validation Run должен сохранять версию Validator и применимого rule-set.

## 12. Migration

Migration — контролируемое преобразование данных из одного технически определённого состояния в другое.

Минимальная модель:

    migration_id
    migration_version
    source_schema
    target_schema
    source_profile_versions
    target_profile_versions
    rules
    reversible
    loss_policy
    tests

## 13. Migration не является новым знанием

Миграция old representation → new representation не должна сама создавать:

- новый Claim;
- новую Evidence Use;
- новую Assessment;
- новую истину;
- новый факт предметного мира.

Если преобразование действительно меняет семантическое содержание, это должно быть явно классифицировано как изменение данных.

## 14. Lossless и lossy migration

Lossless означает, что существенно значимая семантика сохраняется и может быть восстановлена.

Lossy означает, что часть семантики теряется.

При lossy migration обязательно указывается:

- что потеряно;
- почему;
- какие Record затронуты;
- можно ли восстановить исходное представление;
- какие проверки после миграции становятся невозможными.

Полная эквивалентность при существенной потере семантики запрещена.

## 15. Migration report

Каждая миграция должна порождать отчёт:

    migration_id
    source
    target
    processed
    succeeded
    failed
    lossy
    warnings
    errors
    semantic_impact
    output_integrity

Отчёт не изменяет Record сам по себе.

## 16. Dry run

Перед применением миграции должен поддерживаться dry run.

Он показывает:

- затронутые Record;
- изменяемые поля;
- затронутые версии Schema;
- возможные потери;
- warnings;
- errors.

Dry run не изменяет данные.

## 17. Atomicity

Для пакетной миграции необходимо различать:

- успешно мигрированный объект;
- неуспешный объект;
- частично мигрированный пакет.

Нельзя объявлять весь пакет успешным при существенной частичной потере без явного статуса partial.

## 18. Rollback

Если миграция заявлена как reversible, должна существовать проверяемая обратная операция.

Rollback не уничтожает историю применения миграции.

При невозможности rollback это объявляется до применения.

## 19. Idempotency

Для миграций, заявленных как idempotent:

    migrate(migrate(x)) = migrate(x)

Если миграция не idempotent, это должно быть явно указано.

## 20. Migration chain

Цепочка:

    v1 → v2 → v3 → v4

должна иметь явно определённые переходы.

Нельзя предполагать, что v1 → v4 эквивалентно последовательному выполнению всех миграций, если это не проверено.

## 21. Unknown discipline при миграции

Миграция не должна превращать:

    unknown → known
    absent → known
    not_observed → observed
    not_recorded → recorded

без основания в исходных данных.

Новое поле может получить неизвестность, если старое представление не содержало информации для его заполнения.

## 22. Ссылки при миграции

Миграция должна сохранять:

- record_id;
- record_version, если она указана;
- смысл роли ссылки;
- внешние ссылки, если они являются каноническим содержанием.

Историческая ссылка не перенаправляется на текущую версию только потому, что старая версия недоступна.

## 23. Provenance миграции

Сохраняются:

- инструмент;
- версия мигратора;
- migration specification;
- время операции;
- вход;
- результат.

Migration provenance не является предметным доказательством истинности.

## 24. Совместимость

Минимально различаются:

    backward compatible
    forward compatible
    conditionally compatible
    incompatible

Если совместимость неизвестна, она не предполагается.

## 25. Сохранение старого представления

Для долгосрочного проекта желательно сохранять исходное представление при breaking migration, если это разумно.

Минимально должна быть возможность:

- идентифицировать исходную версию;
- определить migration path;
- восстановить исходную семантику;
- установить потери.

## 26. Migration tests

Для каждой миграции обязательны:

- positive fixture;
- negative fixture;
- unknown fixture;
- reference fixture;
- history fixture;
- lossless fixture, если заявлен lossless;
- lossy fixture, если lossy разрешён;
- idempotency test;
- integrity test;
- rollback test, если заявлен reversible.

## 27. Stress tests

Минимум:

- M01 — одна Record;
- M02 — большой набор Record;
- M03 — глубокая version chain;
- M04 — большой reference graph;
- M05 — повреждённый объект;
- M06 — потеря необязательного поля;
- M07 — потеря существенно необходимой семантики;
- M08 — повторный запуск;
- M09 — прерывание процесса;
- M10 — rollback;
- M11 — смешанные версии Schema;
- M12 — смешанные Type Profile versions.

## 28. Безопасность

Мигратор не должен:

- выполнять код из данных;
- доверять непроверенным путям;
- удалять исходные данные до фиксации результата;
- менять Record без журналирования;
- скрывать ошибки;
- повышать неизвестное до известного автоматически.

## 29. Acceptance criteria

008 считается готовым, если:

- разделены все типы версий;
- определено создание новой Record version;
- определены migration metadata;
- разделены lossless/lossy;
- определён migration report;
- есть dry run;
- определены atomicity и partial result;
- определены rollback и idempotency;
- определена история миграций;
- сохранены исторические ссылки;
- сохранена unknown discipline;
- определены migration tests;
- определены stress tests;
- определена безопасность мигратора.

## 30. Инварианты

1. Migration не является источником предметной истины.
2. Schema version не равна Record version.
3. Type Profile version не равна Record version.
4. Standard version не равна Schema version.
5. Validator version не равна Schema version.
6. Новая версия Record не уничтожает старую.
7. Lossy migration не объявляется lossless.
8. Unknown не становится known без основания.
9. Историческая ссылка не перенаправляется автоматически.
10. Rollback не уничтожает историю.
11. Повторная миграция не должна незаметно искажать данные.
12. Migration provenance отделена от provenance предметного содержания.

## 31. Статус

Версия 0.1.

Документ определяет архитектуру версионирования и миграции. Он не является конкретной миграцией и не изменяет Standards.
