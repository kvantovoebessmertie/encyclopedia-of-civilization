# 006 — Архитектура Validator

## Энциклопедия цивилизации

Версия: 0.1  
Класс: Implementation Specification  
Статус: рабочая нормативная спецификация  
Дата: 29 сентября 2026 года

---

## 1. Назначение

Этот документ определяет архитектуру машинной проверки данных Энциклопедии цивилизации.

Validator предназначен для обнаружения нарушений:

- структуры Record;
- зарегистрированного типа и его профиля;
- ссылочной целостности;
- требований применимых Standard;
- версионной и исторической согласованности;
- технической целостности;
- правил импорта, миграции и сборки набора данных.

Validator **не определяет истинность содержания**, не присваивает Record эпистемическую ценность сам по себе и не заменяет человеческое или предметное исследование.

Главный принцип:

> **Validator проверяет соответствие данных определённым правилам. Он не превращает соответствие правилам в истину.**

---

## 2. Место Validator в архитектуре

Каноническая цепочка:

    FOUNDATION
        ↓
    STANDARD
        ↓
    IMPLEMENTATION MODEL
        ↓
    RECORD ENVELOPE
        ↓
    SCHEMA
        ↓
    VALIDATOR
        ↓
    VALIDATION RESULT

Validator является потребителем нормативных правил, а не их источником.

Он не должен самостоятельно создавать:

- новые типы;
- новые семантические роли;
- новые значения полей;
- новые правила истинности;
- новые связи между Record;
- новые значения неизвестности.

Если правило недостаточно определено нормативными документами, Validator должен зафиксировать неопределённость или потребовать отдельного архитектурного решения, а не угадывать.

---

## 3. Что именно проверяется

Validator проверяет соответствие конкретного объекта конкретному набору правил.

Минимально необходимо различать:

    Record
    Record version
    Record Type Profile
    Type Profile version
    Schema version
    Standard version
    Validator version
    Validation run

Они не являются взаимозаменяемыми.

Проверка должна быть воспроизводимой настолько, насколько это возможно для конкретного набора входов.

---

## 4. Принцип слоёв проверки

Проверка разделяется минимум на пять нормативных слоёв.

### L1 — Structural

Проверяет синтаксическую и структурную корректность представления.

Примеры:

- корректный JSON;
- типы значений;
- обязательные поля текущей Schema;
- допустимые перечисления;
- структура массивов и объектов;
- формат идентификаторов, если он задан Schema.

Основной инструмент:

- JSON Schema;
- дополнительные синтаксические проверки.

L1 не устанавливает семантическую истинность.

### L2 — Type and Profile

Проверяет:

- наличие record_type;
- регистрацию типа;
- наличие соответствующего Type Profile;
- поддерживаемость type_version;
- соответствие Record применимому профилю;
- различие между зарегистрированным и технически реализованным типом.

Тип, который зарегистрирован нормативно, но ещё не имеет реализованного Content Profile, не должен автоматически считаться поддерживаемым текущей Schema.

### L3 — Reference Integrity

Проверяет:

- существование целевой Record, когда это требуется;
- существование конкретной версии, если ссылка версионная;
- соответствие целевого типа ограничениям ссылки;
- корректность структурного представления ссылки;
- отсутствие запрещённого разрешения ссылки на другую версию;
- целостность цепочек ссылок и версий.

Неразрешимая ссылка означает нарушение ссылочной целостности, но сама по себе не доказывает, что целевой объект не существовал.

### L4 — Semantic and Standard Rules

Проверяет нормативные инварианты соответствующих Standard и Type Profile.

Примеры:

- Claim не должен быть автоматически превращён в Evidence Use;
- Source не является автоматически доказательством истинности Claim;
- publication_status не является оценкой истинности;
- provenance не является доказательством истинности;
- неизвестное не должно заменяться отсутствием;
- Scope не должен молча превращаться в универсальную применимость;
- Context не должен молча выводиться из текущего пользовательского контекста;
- историческая ссылка не должна молча разрешаться на текущую версию;
- семантика, отсутствующая в исходном материале, не должна создаваться догадкой.

### L5 — Integrity, History and Integration

Проверяет:

- целостность хеша или подписи, если они заявлены;
- согласованность цепочки версий;
- provenance и lineage, когда они обязательны;
- согласованность набора Record;
- импорт и экспорт без заявленной ложной эквивалентности;
- миграции;
- package-level invariants;
- воспроизводимость проверки при одинаковых входах.

L5 не превращает техническую целостность в эпистемическую достоверность.

---

## 5. Граница между Schema и Validator

### JSON Schema отвечает за

- синтаксическую структуру;
- типы данных;
- required;
- enum;
- pattern и иные структурные ограничения;
- структуру вложенных объектов;
- локальные ограничения, которые не требуют знания внешнего графа.

### Validator отвечает за

- ссылки между Record;
- наличие Record в наборе;
- версию целевой Record;
- согласование нескольких Record;
- Type Profile;
- Standard-specific invariants;
- историю;
- provenance;
- миграции;
- package-level consistency;
- правила, зависящие от внешнего состояния или графа.

Не следует помещать в JSON Schema правила, для выполнения которых требуется семантическое предположение или скрытый внешний запрос.

---

## 6. Нормативные границы Validator

Validator НЕ ДОЛЖЕН:

1. считать published равным true;
2. считать draft равным false;
3. считать валидный hash доказательством истинности;
4. считать наличие Source доказательством Claim;
5. выводить record_type из имени файла;
6. выводить Scope из текущего пользователя или интерфейса;
7. выводить Context из текущей даты, местоположения или устройства;
8. заменять неизвестное значение на null без сохранения его семантики;
9. заменять неизвестную версию на текущую;
10. автоматически выбирать одну из конфликтующих Record;
11. автоматически создавать консенсус;
12. исправлять исходные данные молча;
13. менять историческую Record в процессе проверки;
14. считать отсутствие ошибки доказательством истинности;
15. считать отсутствие найденного противоречия доказательством отсутствия противоречий вообще;
16. присваивать эпистемическую оценку только на основании успешной технической проверки.

Validator может обнаружить, что Record соответствует формальным требованиям. Он не может на этом основании утверждать, что её содержание истинно.

---

## 7. Registered, Implemented и Unsupported

Необходимо различать минимум три состояния типа:

    registered
    implemented
    unsupported

### registered

Тип нормативно существует в реестре проекта.

### implemented

Для типа существует технически реализованный Content Profile и Validator может выполнить предусмотренный объём проверки.

### unsupported

Тип может существовать в нормативной модели, но конкретная версия Schema/Validator не поддерживает его технически.

Unsupported не означает:

- ошибочность типа;
- ложность Record;
- недействительность стандарта.

Это означает ограничение текущей реализации.

Для текущей первой вертикальной срезки:

- зарегистрированы 19 типов;
- машинно реализованы 5 Content Profiles:
  record, claim, source, evidence_use, assessment.

---

## 8. Version matrix

Validator должен явно учитывать совместимость версий:

    Schema version
        ↓
    Type Profile version
        ↓
    Standard version
        ↓
    Record version

Отдельно существует версия самого Validator.

Нельзя использовать:

    record_version = schema_version
    record_version = type_version
    type_version = validator_version

Если совместимость между версиями не определена, Validator не должен самостоятельно считать её совместимой.

---

## 9. Validation Run

Каждый запуск проверки должен рассматриваться как отдельный Validation Run.

Run должен позволять установить, когда возможно:

- какой набор данных проверялся;
- какую Schema использовали;
- какие Type Profiles использовали;
- какие версии Standards использовали;
- какую версию Validator использовали;
- какие входные параметры были заданы;
- какие внешние зависимости использовались;
- какие результаты были получены.

Validation Run не изменяет проверяемые Record.

---

## 10. Модель результата проверки

Результат проверки должен отделять:

1. состояние самой Record;
2. найденные нарушения;
3. невозможность проверки;
4. уровень покрытия техническими проверками.

Минимальная логическая модель:

    ValidationResult
    ├── subject
    ├── run
    ├── status
    ├── findings[]
    └── coverage

### status

Минимальные значения:

- pass — применимые проверки выполнены и нарушений, препятствующих прохождению, не найдено;
- fail — обнаружено хотя бы одно нарушение, несовместимое с применимыми правилами;
- indeterminate — существенная часть применимых проверок не может быть выполнена из-за отсутствующих или недоступных входов.

indeterminate не означает ни pass, ни fail.

### coverage

Coverage описывает, какие классы проверок реально были выполнены.

Это необходимо, чтобы:

    не проверено ≠ проверено и прошло

---

## 11. Finding

Каждое обнаружение должно быть структурированным.

Минимальная модель:

    Finding
    ├── code
    ├── severity
    ├── layer
    ├── subject
    ├── rule
    ├── message
    ├── verification_state
    └── locations / references

### severity

Минимально:

- error — нарушение, препятствующее прохождению соответствующей проверки;
- warning — проблема, не делающая объект автоматически невалидным, но требующая внимания;
- info — диагностическая информация.

Severity описывает техническое значение finding, а не истинность Record.

### verification_state

Минимально:

- verified;
- unverified;
- unknown;
- not_applicable.

Verification state не заменяет unknown, absent, not_applicable, not_observed, not_recorded в данных Record. Это отдельная семантика результата проверки.

---

## 12. Unknown discipline в Validator

Validator обязан сохранять различие между:

    unknown
    absent
    not_applicable
    not_observed
    not_recorded

Примеры:

- unknown — значение неизвестно;
- absent — соответствующее значение отсутствует по смыслу;
- not_applicable — поле или свойство неприменимо;
- not_observed — объект/свойство не было наблюдено;
- not_recorded — значение могло существовать, но не было записано.

Validator не должен преобразовывать одно состояние в другое без нормативного основания.

---

## 13. Неизвестность проверки

Нужно различать:

    unknown value
    ≠
    unknown validation

Например:

- неизвестна дата события — это свойство Record;
- невозможно проверить существование внешнего источника — это ограничение Validation Run.

Они должны оставаться различимыми.

---

## 14. Ошибка данных и невозможность проверки

Следует различать:

### Invalid

Данные нарушают известное применимое правило.

### Unverifiable

Данные нельзя проверить из-за отсутствующего или недоступного необходимого входа.

### Unknown

Семантика или значение неизвестны, но это само по себе может быть допустимым состоянием.

### Conflict

Два или более доступных утверждения/состояния находятся в отношении противоречия согласно применимому правилу.

Conflict не означает автоматически, что один из участников ложен.

---

## 15. Детерминированность

При одинаковых:

- входных данных;
- версиях Schema;
- версиях Type Profiles;
- версиях Standards;
- версии Validator;
- конфигурации;
- доступных внешних зависимостях;

результат должен быть детерминированным.

Если внешнее состояние изменилось, это должно быть отражено в Validation Run.

Validator не должен скрыто обращаться к меняющимся внешним данным, если результат заявляется как воспроизводимый offline.

---

## 16. Offline-first

Архитектура Validator должна поддерживать работу без сети.

Минимально offline должны быть доступны:

- Schema;
- Type Profiles;
- применимые нормативные правила;
- Validator;
- локальный набор Record;
- необходимые справочники;
- локальные криптографические материалы, если они используются.

Внешняя ссылка не должна быть единственным способом проверить локальную структурную целостность.

Если внешняя проверка необходима и недоступна, результат должен отражать это как неполную проверяемость, а не скрывать ограничение.

---

## 17. Порядок выполнения

Рекомендуемый порядок:

    1. Parse
    2. L1 Structural
    3. L2 Type/Profile
    4. L3 Reference Integrity
    5. L4 Semantic/Standard
    6. L5 Integrity/History/Integration
    7. Aggregate Result

Порядок является архитектурной зависимостью, а не способом скрыть ошибки.

### Продолжение после ошибки

Validator должен по возможности продолжать независимые проверки.

Например:

- ошибка одного поля не должна мешать проверке независимой Record;
- отсутствие одной внешней ссылки не должно скрывать структурные ошибки;
- невозможность L3 не должна автоматически называться провалом L4, если L4 можно выполнить независимо.

Однако если нижний слой делает верхний слой технически невозможным, соответствующий верхний слой должен получить состояние unverifiable или not_run, а не искусственный pass.

---

## 18. Dependency graph

Проверки могут иметь зависимости.

Пример:

    Schema validity
          ↓
    Type Profile
          ↓
    Reference resolution
          ↓
    Semantic relation checks
          ↓
    History / lineage

Если зависимая проверка не выполнена, Validator должен сохранять причину.

Запрещено молча превращать:

    not_run → pass

---

## 19. Проверка ссылок

Структурная ссылка должна иметь различимую модель для:

- record_id;
- record_version, если требуется;
- типа ссылки/роли, если она нормативно значима;
- внешнего ресурса, если это не внутренняя Record.

Принцип:

> **Ссылка без указанной версии не должна интерпретироваться как ссылка на конкретную историческую версию, если правила требуют исторической точности.**

Если ссылка указывает только на record_id, Validator может разрешить текущую версию только там, где это разрешено семантикой конкретного профиля.

---

## 20. Проверка истории версий

Validator должен проверять, насколько это применимо:

- уникальность пары record_id + record_version;
- согласованность predecessor/successor;
- отсутствие невозможных циклов в цепочке версий;
- сохранение исторических ссылок;
- наличие основания изменения, когда оно обязательно;
- отсутствие тихого перезаписывания версии.

Создание новой версии не должно автоматически изменять старую.

---

## 21. Проверка provenance

Validator проверяет структуру provenance и её обязательность по применимому профилю.

Он не должен выводить:

    есть автор → содержание истинно
    есть источник → утверждение доказано
    есть подпись → утверждение верно

Если provenance ссылается на Record, эта ссылка проверяется по обычным правилам ссылочной целостности.

---

## 22. Проверка publication_status

Validator может проверить:

- допустимость значения;
- соответствие переходов жизненного цикла, если они определены;
- обязательность дополнительных полей для конкретного статуса.

Validator не должен интерпретировать:

    published = true
    withdrawn = false
    archived = refuted

Такие преобразования запрещены.

---

## 23. Проверка Claim

Для Claim Validator должен проверять только правила, заданные применимым Claim Standard и Type Profile.

В частности, нельзя автоматически считать Claim:

- истинным;
- доказанным;
- согласованным с проектом;
- поддержанным Source только из-за наличия ссылки на Source.

Связь Evidence Use проверяется как отдельная Record/семантическая конструкция.

---

## 24. Проверка Source

Source должен проверяться как объект источниковой информации согласно своему Standard.

Validator не должен автоматически переносить свойства Source на утверждения, использующие Source.

Например:

    Source exists
    ≠
    Claim supported

Сила, релевантность и достаточность Evidence Use относятся к применимым правилам оценки свидетельства, а не выводятся из самого факта существования Source.

---

## 25. Проверка Evidence Use

Evidence Use должна проверяться отдельно от Source и Claim.

Минимально Validator должен различать:

    source
    claim
    evidence_use

Наличие Evidence Use не означает автоматически истинность Claim.

Если Evidence Use имеет роль supports или contradicts, роль должна проверяться по допустимым значениям применимого Standard.

Нельзя превращать:

    supports → true
    contradicts → false

для самого Claim без отдельного правила оценки.

---

## 26. Проверка Assessment

Assessment является отдельной Record и не должен автоматически становиться:

- Claim;
- Evidence Use;
- Decision;
- Truth;
- Consensus;
- endorsement проекта.

Validator проверяет соответствие Assessment его Standard и профилю.

Наличие результата Assessment не является само по себе доказательством результата.

---

## 27. Семантические конфликты

Validator может обнаружить конфликт, если применимое нормативное правило позволяет его определить.

Например:

- две Record заявляют несовместимые значения при одинаковой явно заданной семантике;
- ссылка требует конкретную версию, а указана другая;
- поле нарушает инвариант профиля.

Но Validator не должен разрешать конфликт посредством:

- приоритета более новой Record;
- приоритета published;
- приоритета локального файла;
- количества повторений;
- собственного предпочтения.

Разрешение конфликта является отдельным процессом.

---

## 28. Множественность знания

Одновременное существование нескольких несовместимых Claim не является автоматически ошибкой базы.

Например:

    Claim A
    Claim B
    A contradicts B

может быть корректным представлением состояния знания.

Ошибка возникает только при нарушении конкретного инварианта, запрещающего такую конфигурацию.

Validator не должен принудительно создавать единый консенсус.

---

## 29. Aggregation и derived results

Производная Record должна сохранять происхождение и, когда применимо, входные Record.

Validator должен различать:

    input
    derived result
    source
    provenance

Производный результат не становится независимым свидетельством своего собственного вывода.

Циклическая зависимость должна обнаруживаться там, где применимое правило запрещает её.

---

## 30. Импорт и миграция

Импортированная информация должна сохранять известную степень семантической точности.

Если импорт не позволяет установить исходную семантику, Validator не должен её придумывать.

Допустимы:

- частичный импорт;
- импорт с потерями;
- неизвестное поле;
- отложенная проверка.

Недопустимо заявлять полную эквивалентность, если существенно необходимая семантика была потеряна.

Миграция формата не должна автоматически создавать новый эпистемический акт.

---

## 31. Исправление данных

Validator по умолчанию является read-only.

Он:

- обнаруживает нарушение;
- описывает нарушение;
- локализует нарушение;
- сообщает применимое правило.

Он не должен молча:

- менять Record;
- удалять данные;
- заменять значения;
- перепривязывать ссылки;
- выбирать версию;
- создавать provenance.

Автоматические исправления допустимы только как отдельная явно объявленная операция миграции/repair с собственной историей и результатом.

---

## 32. Error codes

Коды ошибок должны быть стабильными идентификаторами правил.

Рекомендуемый формат:

    VAL-L1-...
    VAL-L2-...
    VAL-L3-...
    VAL-L4-...
    VAL-L5-...

Код должен идентифицировать правило, а не конкретный текст сообщения.

Текст сообщения может уточняться без изменения кода, если семантика правила не изменилась.

Примеры:

    VAL-L1-SCHEMA-REQUIRED
    VAL-L1-SCHEMA-TYPE
    VAL-L2-UNKNOWN-TYPE
    VAL-L2-UNSUPPORTED-PROFILE
    VAL-L2-TYPE-VERSION
    VAL-L3-REFERENCE-MISSING
    VAL-L3-REFERENCE-VERSION
    VAL-L3-REFERENCE-TYPE
    VAL-L4-RULE-VIOLATION
    VAL-L4-UNKNOWN-SEMANTICS
    VAL-L5-VERSION-CHAIN
    VAL-L5-INTEGRITY
    VAL-L5-PROVENANCE
    VAL-L5-PACKAGE-CONSISTENCY

Список кодов является расширяемым.

Удаление или изменение смысла существующего кода требует версионируемого изменения Validator Rules.

---

## 33. Severity не должна скрывать слой

Один и тот же error может возникать на разных слоях.

Поэтому Finding должен содержать одновременно:

    severity
    layer
    code
    rule

Например:

    severity = error
    layer = L3
    code = VAL-L3-REFERENCE-VERSION

Это позволяет отделить структурную ошибку от семантического нарушения.

---

## 34. Validation coverage

Результат проверки должен позволять ответить:

- какие слои были выполнены;
- какие правила применялись;
- какие правила были пропущены;
- почему они были пропущены;
- какие внешние зависимости были недоступны.

Coverage не является процентом «истинности».

Не следует использовать:

    validation = 95%

как эквивалент «95% истины».

---

## 35. Пакетная проверка

Validator должен поддерживать как минимум:

- проверку одной Record;
- проверку набора Record;
- проверку графа ссылок;
- проверку исторической цепочки;
- проверку экспортного пакета.

Пакетная проверка должна различать:

    record-local failure
    package-level failure
    dependency failure

Ошибка одного объекта не должна автоматически объявлять все остальные объекты невалидными.

---

## 36. Проверка набора Record

Для набора данных Validator может проверять:

- уникальность идентичностей;
- уникальность версий;
- ссылочную целостность;
- совместимость типов;
- отсутствие недопустимых дубликатов;
- согласованность version chain;
- package manifest, если он используется;
- целостность зависимостей.

Проверка набора не должна создавать новые семантические отношения.

---

## 37. Криптографическая целостность

Если Record или пакет содержит digest/signature, Validator может проверить:

- соответствие заявленного алгоритма;
- корректность вычисленного digest;
- корректность подписи при наличии необходимых ключей;
- соответствие каноническому представлению.

Успешная криптографическая проверка означает:

    representation integrity verified

а не:

    semantic truth verified

---

## 38. Безопасность

Validator должен рассматриваться как недоверенный обработчик входных данных.

Он должен:

- ограничивать ресурсы;
- обрабатывать циклы;
- предотвращать бесконечные рекурсивные проверки;
- безопасно обрабатывать большие Record;
- безопасно обрабатывать повреждённые данные;
- не выполнять произвольный код из Record;
- не доверять внешним идентификаторам без проверки;
- разделять данные и инструкции.

Внешний текст Record не должен становиться исполняемой инструкцией Validator.

---

## 39. Производительность и глубина

Проверка должна иметь явно определяемую глубину.

Например:

    local
    → referenced
    → transitive
    → package

Если проверена только локальная Record, Validator не должен заявлять полную графовую проверку.

Ограничение глубины должно быть отражено в Validation Run.

---

## 40. Кэширование

Кэширование результатов допустимо только при сохранении зависимости от:

- Record version;
- Schema version;
- Type Profile version;
- Standard version;
- Validator version;
- конфигурации;
- внешних зависимостей.

Изменение любого существенного входа должно инвалидировать соответствующий кэш.

---

## 41. Расширяемость

Новые правила могут добавляться без изменения базовой модели Validator.

Правило должно иметь:

- стабильный идентификатор;
- применимость;
- версию;
- описание;
- уровень;
- условия проверки;
- ожидаемый результат;
- семантику failure/indeterminate, если применимо.

Новый профиль может усиливать требования, но не должен молча отменять инварианты более высокого нормативного уровня.

---

## 42. Совместимость Validator

Версии Validator должны иметь явно определяемую совместимость.

Минимально нужно различать:

    Validator implementation version
    Validator rule-set version
    Schema version
    Type Profile version
    Standard version

Изменение алгоритма проверки, которое может изменить результат существующей проверки, должно быть отслеживаемым по версии.

---

## 43. Результаты проверки не являются Record

ValidationResult не должен автоматически становиться обычной Record предметного знания.

Если проект захочет сохранять результаты проверок как исторические артефакты, для них должен быть определён отдельный профиль/тип или нормативный механизм хранения.

Сам факт прохождения Validator не должен менять исходную Record.

---

## 44. Стресс-тесты архитектуры

Validator Architecture считается устойчивой только после прохождения минимум следующих сценариев.

### T01 — Минимальная Record

Валидная Record с минимально необходимыми полями.

Ожидание: L1 проходит при соответствии Schema.

### T02 — Неверный record_type

Указан незарегистрированный тип.

Ожидание: L2 failure.

### T03 — Registered but unsupported

Указан зарегистрированный, но ещё не реализованный тип.

Ожидание: L2 сообщает unsupported; система не называет тип ложным.

### T04 — Неверный publication_status

Неизвестное значение статуса.

Ожидание: L1 failure.

### T05 — Published claim

Claim имеет publication_status = published.

Ожидание: Validator не выводит истинность Claim.

### T06 — Source exists

Source существует, Claim ссылается на него, но Evidence Use отсутствует.

Ожидание: Source не считается автоматически поддержкой Claim.

### T07 — Evidence supports

Evidence Use имеет роль supports.

Ожидание: проверяется роль; Claim не становится автоматически истинным.

### T08 — Version-specific reference

Ссылка требует конкретную версию, которой нет в наборе.

Ожидание: L3 failure или indeterminate в зависимости от характера недоступности.

### T09 — Current-version substitution

Историческая ссылка не должна молча разрешиться на текущую версию.

Ожидание: нарушение L3 при требовании исторической точности.

### T10 — Unknown value

Поле имеет семантику unknown.

Ожидание: Validator не превращает его в absent.

### T11 — Unknown validation

Внешний ресурс недоступен.

Ожидание: результат проверки отражает indeterminate/unverified, а не pass.

### T12 — Conflicting Claims

Два Claim противоречат друг другу.

Ожидание: конфликт фиксируется, но единый Claim не выбирается автоматически.

### T13 — Version chain

Создана новая версия Record.

Ожидание: старая версия остаётся разрешимой.

### T14 — Hash valid

Digest совпадает.

Ожидание: техническая целостность проходит; истинность не устанавливается.

### T15 — Provenance present

Есть provenance.

Ожидание: provenance проверяется структурно; истинность содержания из него не выводится.

### T16 — Malformed input

Повреждённый JSON.

Ожидание: L1 failure без попытки угадать содержимое.

### T17 — Semantic dependency unavailable

L1 проходит, но внешний нормативный словарь недоступен.

Ожидание: соответствующая проверка не маскируется под pass.

### T18 — Repair attempt

Validator обнаруживает ошибку.

Ожидание: исходная Record не изменяется.

### T19 — Reproducibility

Повторная проверка с теми же входами.

Ожидание: эквивалентный результат и идентифицируемый Validation Run.

### T20 — Lossy import

Импорт потерял существенно необходимое поле.

Ожидание: неизвестность/непроверяемость сохраняется; полная эквивалентность не заявляется.

---

## 45. Инварианты Validator

Минимальные инварианты:

1. Validator не является источником семантики.
2. Structural validity не равна semantic truth.
3. Registered type не равен implemented type.
4. Record version не равна Type Profile version.
5. Type Profile version не равна Schema version.
6. Validation failure не равен falsehood Record.
7. Validation pass не равен truth Record.
8. Unverifiable не равен pass.
9. Unknown не равен absent.
10. Conflict не требует автоматического выбора победившей стороны.
11. Source не становится автоматически Evidence.
12. Evidence Use не делает Claim автоматически истинным.
13. publication status не является epistemic assessment.
14. Provenance не является доказательством истинности.
15. Hash/signature validity не является доказательством истинности.
16. Историческая ссылка не должна молча разрешаться на другую версию.
17. Validator не изменяет проверяемые данные по умолчанию.
18. Непроверенный слой не должен объявляться пройденным.
19. Результат должен быть связан с конкретными версиями применимых правил.
20. Offline-проверка должна быть возможна для тех правил, для которых все необходимые локальные входы доступны.

## 46. Критерии готовности

IMPLEMENTATION/006 считается реализованным архитектурно, если:

- определены границы Schema и Validator;
- определены L1–L5;
- определены registered/implemented/unsupported;
- разделены Record, Type Profile, Schema, Standard и Validator versions;
- определена модель Validation Run;
- определены pass, fail, indeterminate;
- различаются invalid, unverifiable, unknown и conflict;

- определена offline-first модель;
- определены правила ссылочной и исторической проверки;
- определены правила для первых пяти реализованных типов;
- определена политика импорта и миграции;
- определена read-only модель;
- определены стабильные error codes;
- выполнены T01–T20;
- проведён интеграционный аудит с IMPLEMENTATION/001–005.

## 50. Матрица ответственности Standard → Schema → Validator → Pipeline

Правило формализации: не каждое нормативное правило Standard является правилом отказа Validator. Перед добавлением машинной проверки каждое требование должно быть отнесено к одному из классов:

| Класс | Где проверяется | Результат |
|---|---|---|
| Структурное обязательное требование | Schema (L1/L2) | fail при нарушении структуры |
| Локальное семантическое обязательное требование | Validator L4 | fail с устойчивым кодом |
| Ссылочное/историческое требование | Validator L3/L5, Resolver | fail или indeterminate |
| Интеграционное требование преобразования | Migration / Publication / Recovery / Storage | проверяется соответствующим компонентом |
| Anti-inference правило | Validator/Integration tests | запрет автоматического вывода, а не обязательное поле |
| Контекстно-зависимое правило | профиль/доменный Validator при наличии условий применимости | проверяется только при доказанной применимости |
| Неформализуемое без внешнего контекста правило | сохраняется нормативно; не превращается в универсальный required | indeterminate или вне локального Validator |

### 50.1. STANDARD/011–018: базовые обязательства

| Standard | Базовое машинное обязательство | Текущая реализация | Статус |
|---|---|---|---|
| 011 State | subject_ref, state_content; применимая рамка при её наличии | Schema + L4 | PASS |
| 012 Process | process_content; участники/контекст/время — когда представлены | Schema + L3/L4 | PASS для формализуемого ядра |
| 013 Relation | relation_type, минимум 2 участника; роли/направление/рамка — когда представлены | Schema + L3/L4 | PASS для формализуемого ядра |
| 014 Identity | identity_level, минимум 2 targets, criterion; scope/evidence — когда представлены | Schema + L3/L4 | PASS для формализуемого ядра |
| 015 Context | context_content, target_ref; scope/status/preconditions — когда представлены | Schema + L3/L4 | PASS для формализуемого ядра |
| 016 Scope | target_ref, scope_content; universe/level/membership rule — когда применимы | Schema + L3/L4 | PASS для формализуемого ядра |
| 017 Provenance | target_ref, relation; inputs/outputs/agent/method/status/fidelity — когда применимы | Schema + L3/L4 | PASS для формализуемого ядра |
| 018 Authorship/Contribution | target_ref, contributor_ref, contribution; остальные измерения — по применимому профилю | Schema + L3/L4 | PASS для формализуемого ядра |

### 50.2. Что намеренно не превращается в универсальные ошибки Validator

Следующие семейства правил 011–018 требуют сопоставления семантических ролей, временных рамок, предметной области, Scope/Context, внешних источников или истории преобразования и потому не могут безопасно проверяться как безусловные поля:

- «когда это существенно»;
- «когда применимо»;
- сохранение различия наблюдаемого/измеренного/выведенного/модельного/реконструированного происхождения;
- отсутствие автоматического обобщения от выборки к популяции;
- различение роли, а не только значения поля;
- сохранение исторической неопределённости;
- fidelity после перевода, сжатия, миграции или публикации;
- отсутствие причинного вывода из временной последовательности или корреляции;
- сохранение альтернативных идентичностей и конкурирующих атрибуций;
- различение «неизвестно», «не зафиксировано», «неприменимо», «ограничено» и «утеряно» при отсутствии достаточного контекста.

Эти правила являются нормативными инвариантами, но не должны искусственно превращаться в локальные обязательные поля. Их enforcement должен находиться на том слое, где имеется необходимый контекст.

### 50.3. Критерий закрытия semantic conformance

Semantic conformance для 011–018 может быть повышен только после того, как для каждого нормативного правила определены:

1. идентификатор правила;
2. класс формализации;
3. компонент, ответственный за enforcement;
4. устойчивый Finding/error code, если правило машинно диагностируемо;
5. fixture/test;
6. условия применимости;
7. причина, если правило намеренно не проверяется локальным Validator.

## 18. Фактическое покрытие Reference Validator: L4/L5

После реализации первого полного L4/L5 enforcement-пакета Reference Validator выполняет:

### L4
- обязательные семантические поля для завершённых Assessment / Inference / Decision;
- разрешимость атрибуции завершённого Inference по режимам known/reconstructed;
- Evidence Role;
- Source identity;
- применимые рамки State / Process / Relation / Identity;
- границы Identity и candidate_refs для неокончательного разрешения;
- typed semantic boundaries уже реализованы отдельным ReferenceResolver;
- анти-инференсные запреты для publication/truth и побочного создания truth другим типом;
- causal attribution для Result не принимается без явно сохранённого basis_ref;
- planned/predicted Event не принимается как автоматически observed.

### L5
- проверка заявленной Record integrity;
- поддержка sha256;
- каноникализация json-sort-keys-utf8-excluding-integrity;
- обнаружение несовпадения digest;
- честный статус indeterminate для неподдерживаемого алгоритма/canonicalization вместо ложного PASS;
- проверка порядка valid_time.start <= valid_time.end;
- обнаружение дубликатов одной логической Record version на уровне Dataset;
- Dataset L5 выполняется после полного восстановления snapshot.

### Граница
L5 Record не заявляет полноту графовой/пакетной проверки. ReferenceResolver отвечает за L3 graph/reference integrity, а recovery/package layer — за manifest/file integrity. Эти результаты не смешиваются с утверждением истинности содержания.

integrity исключается из собственной canonical representation перед вычислением digest; это предотвращает циклическую зависимость digest от самого себя.
