# 009 — Канонический переносимый пакет

## Энциклопедия цивилизации

Версия: 0.1  
Класс: Implementation Specification  
Статус: рабочая нормативная спецификация  
Дата: 29 сентября 2026 года

---

## 1. Назначение

Portable Package должен позволять:

- сохранить проект независимо от конкретной платформы;
- перенести набор Record;
- проверить целостность;
- восстановить Schema и Type Profiles;
- выполнить Validator offline;
- восстановить историю;
- определить совместимость;
- собрать публикационное представление.

Главный принцип:

> **Пакет должен быть самодостаточным настолько, насколько это необходимо для независимой проверки и восстановления.**

## 2. Каноническая цель

Portable Package не является публикацией.

Разделение:

    Canonical Data
        ↓
    Portable Package
        ↓
    Validation
        ↓
    Publication / Representation

PDF, сайт, GitHub-интерфейс или иное представление не являются заменой пакету.

## 3. Состав пакета

Минимальная логическая структура:

    package/
    ├── manifest
    ├── records/
    ├── schemas/
    ├── profiles/
    ├── standards/
    ├── validators/
    ├── migrations/
    ├── integrity/
    ├── fixtures/
    └── recovery/

Конкретный layout может изменяться, если сохраняется установленная семантика.

## 4. Manifest

Manifest должен позволять определить:

- package_id;
- package_version;
- дату сборки;
- применимую Schema;
- Type Profiles;
- Standards;
- Validator;
- список компонентов;
- integrity metadata;
- compatibility;
- recovery metadata.

Manifest не должен содержать скрытую семантику, существующую только в интерфейсе.

## 5. Package version

package_version относится к упаковке, а не к Record.

Изменение layout не создаёт автоматически новую Record version.

Изменение канонических данных должно быть отдельно обнаружимо.

## 6. Records

Пакет должен содержать канонические Record либо однозначно включённые локальные компоненты, если такой режим определён.

Каждая Record должна сохранять:

- record_id;
- record_type;
- record_version;
- type_version;
- schema;
- publication_status;
- provenance;
- специализированное содержание;
- релевантные Scope, Context, Time и Integrity.

## 7. История

Если пакет заявляет историческую полноту, необходимые версии Record должны быть включены.

Текущая версия не заменяет исторические версии молча.

Manifest должен позволять определить, является ли пакет:

- current snapshot;
- historical snapshot;
- partial export;
- complete archive.

## 8. Partial package

Частичный пакет допустим.

Он должен явно указывать:

- что включено;
- что исключено;
- какие ссылки могут быть внешними;
- какие проверки невозможно выполнить;
- какие зависимости отсутствуют.

Partial package не должен выдавать себя за полный архив.

## 9. Reference closure

Для полного архивного пакета предпочтительно обеспечить замыкание внутренних ссылок:

    Record A
       ↓
    Record B
       ↓
    Record C

необходимые внутренние зависимости должны присутствовать.

Если замыкание невозможно, manifest описывает внешние зависимости.

## 10. Schema и Type Profiles

Пакет должен включать версии Schema и Type Profiles, необходимые для проверки содержащихся Record.

Нельзя полагаться только на внешний URL.

Если компонент отсутствует локально, это отражается в package completeness.

## 11. Standards

Для долгосрочной автономности пакет должен включать нормативные документы, необходимые для интерпретации заявленной версии данных, либо их неизменяемые локальные копии.

Изменение Standard после сборки не должно молча менять смысл исторического пакета.

## 12. Validator

Пакет должен содержать:

- Validator;
- либо точную ссылку на воспроизводимую версию;
- либо другой проверяемый механизм получения идентичного инструмента.

Для автономного архива предпочтительны локальные воспроизводимые артефакты.

## 13. Migrations

Если пакет содержит данные нескольких поколений, должны быть доступны:

- migration metadata;
- migration specifications;
- порядок переходов;
- lossless/lossy политика;
- результаты миграции, если они сохранены.

Миграция не является единственным способом понять историческую Record.

## 14. Integrity

Для каждого существенного компонента должен существовать проверяемый механизм целостности:

    component
        ↓
    digest
        ↓
    manifest
        ↓
    package integrity result

Алгоритм digest указывается явно.

Успешная integrity проверка не означает истинность содержания.

## 15. Каноническое представление

Для проверки целостности необходимо определить canonical representation либо другой детерминированный способ получения одинакового digest.

Изменения порядка полей, кодировки и переносов строк должны быть урегулированы canonicalization rule.

Техническая каноникализация не должна создавать новую семантику.

## 16. Порядок загрузки

Рекомендуемый порядок:

    1. read manifest
    2. verify package metadata
    3. verify component integrity
    4. load schemas
    5. load profiles
    6. load standards
    7. load records
    8. resolve references
    9. run validator
    10. produce recovery report

Ошибка раннего этапа не должна маскироваться под успешную загрузку.

## 17. Offline recovery

Минимальный flow:

    package
      ↓
    clean environment
      ↓
    integrity verification
      ↓
    schema/profile loading
      ↓
    records loading
      ↓
    reference resolution
      ↓
    validation
      ↓
    reconstruction

Recovery должен быть возможен без исходного сервера, если пакет заявлен как self-contained.

## 18. Recovery Report

Recovery Report должен позволять установить:

- package_id;
- package_version;
- integrity result;
- количество загруженных Record;
- количество версий;
- разрешённые ссылки;
- неразрешённые ссылки;
- применённые Schema;
- применённые Profiles;
- ValidationResult;
- внешние зависимости;
- ограничения восстановления.

## 19. Reproducibility

Для одинакового пакета, одинаковой конфигурации и одинаковых версий инструментов recovery должен давать эквивалентный результат.

Если воспроизводимость невозможна из-за внешней зависимости, это явно отражается.

## 20. Storage independence

Пакет не должен зависеть от конкретной:

- СУБД;
- облачной платформы;
- веб-сервера;
- GitHub;
- операционной системы,

если заявлена переносимость.

Платформа может доставлять пакет, но не является источником его семантики.

## 21. Publication independence

Из одного пакета могут строиться:

    package
      ├── web
      ├── PDF
      ├── print
      ├── offline reader
      └── API

Изменение представления не должно изменять канонические Record.

## 22. Package completeness

Нужно различать:

    complete
    partial
    dependency-incomplete
    corrupted

complete — все заявленные необходимые компоненты доступны и целостны.

partial — пакет сознательно содержит только часть данных.

dependency-incomplete — отсутствуют необходимые зависимости.

corrupted — нарушена техническая целостность существенного компонента.

Эти состояния не являются оценкой истинности данных.

## 23. Security

Пакет должен безопасно обрабатываться в недоверенной среде.

Нельзя:

- выполнять код из Record;
- автоматически запускать произвольные scripts;
- доверять путям из manifest без нормализации;
- разрешать path traversal;
- считать имя файла доказательством идентичности;
- автоматически открывать внешние ресурсы без политики.

## 24. Размер и фрагментация

Пакет может быть разбит на части.

При этом сохраняются:

- package identity;
- component identity;
- порядок и зависимости;
- integrity;
- возможность проверки части;
- возможность восстановления полного пакета.

Фрагментация не меняет Record identity.

## 25. Архивирование

Для долговременного хранения желательно иметь:

- основной архив;
- независимую копию;
- integrity verification;
- описание форматов;
- описание инструментов;
- recovery instructions;
- version metadata.

Один физический носитель не является достаточной стратегией сохранности сам по себе.

## 26. Tests

Минимально:

- P01 — полный пакет проходит integrity;
- P02 — повреждённый Record обнаруживается;
- P03 — повреждённая Schema обнаруживается;
- P04 — повреждённый manifest обнаруживается;
- P05 — отсутствующая зависимость даёт dependency-incomplete;
- P06 — историческая версия восстанавливается;
- P07 — отсутствующая Record обнаруживается;
- P08 — пакет загружается без сети;
- P09 — повторное восстановление даёт эквивалентный результат;
- P10 — публикация строится без изменения Record;
- P11 — partial package не объявляется complete;
- P12 — path traversal не выполняется.

## 27. Stress tests

- P13 — большой пакет Record;
- P14 — большой reference graph;
- P15 — большая история версий;
- P16 — много фрагментов одного пакета;
- P17 — повреждение нескольких компонентов;
- P18 — смешение compatible и incompatible Schema;
- P19 — большой Unicode-текст;
- P20 — восстановление на чистой машине.

## 28. Acceptance criteria

009 считается готовым, если:

- определён Portable Package;
- определён manifest;
- определён package_version;
- разделены current/historical/partial/complete exports;
- определено reference closure;
- Schema, Profile, Standard и Validator не теряются;
- определена integrity model;
- определён offline recovery;
- определён Recovery Report;
- определена воспроизводимость;
- обеспечена storage independence;
- обеспечена publication independence;
- определена security model;
- определены P01–P20;
- пакет не смешивается с канонической семантикой Record.

## 29. Инварианты

1. Package version не равна Record version.
2. Package layout не является семантикой Record.
3. Partial package не является complete archive.
4. Integrity не равна truth.
5. Manifest не является заменой Record.
6. Отсутствующая зависимость не маскируется под успешную проверку.
7. Историческая версия не заменяется текущей.
8. Offline recovery не требует исходного сервера для self-contained пакета.
9. Публикация не меняет канонические Record.
10. Пакет не выполняет данные как код.

## 31. Языковое правило

Нормативный текст проекта должен быть преимущественно на русском языке.

Английские термины допускаются как технические идентификаторы, имена полей, файлов, кодов и компонентов.

Английский термин не должен заменять необходимое русское определение.

## 32. Статус

Версия 0.1.

Документ определяет архитектуру переносимого пакета и восстановления. Он не является конкретным форматом архивного файла и не привязывает проект к одному инструменту упаковки.
