# 003 — Реестр типов

## Энциклопедия цивилизации

Версия: 0.1  
Статус: рабочий нормативный документ

---

## 1. Назначение

Этот документ определяет канонический реестр типов Record, используемых машиночитаемой реализацией проекта.

Реестр связывает:

```
record_type
    ↓
нормативный Standard
    ↓
семантика Content
    ↓
правила ссылок и валидации
```

Реестр не создаёт новых фундаментальных сущностей.

Он фиксирует уже принятые типы и их технические идентификаторы.

---

## 2. Основные правила

### 2.1. Тип является явным

Каждая Record должна содержать явный `record_type`.

Тип не выводится только из:

- имени файла;
- пути;
- заголовка;
- расширения;
- таблицы базы данных;
- текста содержания.

### 2.2. Тип не равен Referent

`record_type` описывает тип записи, а не автоматически тип предмета мира.

Например:

```
record_type = claim
```

означает, что Record представляет Claim.

Это не означает, что Claim является физическим объектом или отдельной Core Entity.

### 2.3. Тип не равен семантической роли

Наличие специализированного стандарта не означает автоматически наличие новой сущности ядра.

Особенно это относится к:

- Result;
- State;
- Evidence Use;
- Assessment;
- Relation;
- Context;
- Scope;
- Provenance.

Их нормативная семантика может быть реализована как Record, роль, структурированное содержание или связь в соответствии с соответствующим Standard.

### 2.4. Один идентификатор — одна семантическая ответственность

Идентификатор типа не должен использоваться одновременно для разных нормативных смыслов.

Изменение существенной семантики существующего типа требует новой версии типа либо отдельного архитектурного решения.

## 3.1. Версии профилей

Все типы имеют профиль `1.0`, кроме `trust_reputation`, для которого после ADR-0005 действует профиль `1.1`. Версия профиля не заменяет `record_version` или `schema_version`.

────────

## 4. Смысл кодов

Числовой номер Standard и машинный идентификатор типа связаны реестром, но не должны считаться одним и тем же идентификатором.

Например:

```
STANDARD/002-CLAIM.md
        ↓
record_type = "claim"
```

Имя файла может измениться без изменения `record_type`, если архитектурное решение не требует изменения идентичности типа.

Это обеспечивает независимость данных от расположения файлов.

---

## 5. Специальный случай Record

`record` является базовым типом, соответствующим универсальной единице хранения.

Он не должен использоваться как обход специализированной типизации.

Если содержание соответствует Claim, Source, Event или другому зарегистрированному типу, запись должна использовать соответствующий специализированный тип.

`record` может использоваться там, где:

- специализированный тип ещё не определён;
- запись действительно содержит только общую оболочку;
- архитектурное правило допускает временную типизацию.

Такая возможность не должна превращаться в способ обхода требований специализированного Standard.

---

## 6. Типы и Core Model

Реестр не расширяет список Core Entities.

В частности:

```
result
state
relation
context
scope
provenance
```

не должны автоматически трактоваться как самостоятельные фундаментальные сущности мира только потому, что для них существуют типы Record.

Это следует из FOUNDATION/003-ADR и FOUNDATION/006-CORE-MODEL.

---

## 7. Типы и Referent

Одна Record может относиться к одному или нескольким Referent в зависимости от своего типа и содержания.

Например:

```
Claim
    → относится к Referent

Event
    → описывает событие или утверждение о событии

State
    → представляет состояние относительно определённого носителя

Relation
    → описывает отношение между определёнными участниками
```

Это не означает, что Record и Referent имеют одну идентичность.

```
record_id ≠ referent_id
```

Если Record содержит ссылку на Referent, эта ссылка должна иметь отдельную структурную семантику.

---

## 8. Типы и семантические роли

Тип Record определяет основной нормативный профиль записи.

Но внутри Content могут присутствовать семантические роли.

Например, Record типа `assessment` может иметь:

- объект оценки;
- критерий;
- основание;
- результат;
- неопределённость.

Наличие поля `result` внутри Assessment не означает, что вся Assessment становится Record типа `result`.

Следует различать:

```
record_type
≠
field role
≠
referent type
```

Это правило особенно важно для JSON Schema, чтобы структура полей не порождала скрытых сущностей.

---

## 9. Типы и ссылки

Допустимые ссылки будут определяться двумя уровнями:

### Общий уровень

Envelope допускает структурные ссылки, если они необходимы общей модели.

### Специализированный уровень

Каждый Standard определяет:

- какие типы могут быть целями;
- какие типы могут быть источниками;
- обязательна ли ссылка;
- может ли она указывать на конкретную версию;
- является ли отношение версионно-зависимым.

Запрещается выводить допустимость ссылки только из совпадения строковых идентификаторов.

---

## 10. Версия типа

Каждый зарегистрированный тип имеет собственную версию семантического профиля (`type_version`). Все 19 зарегистрированных типов на текущем этапе имеют реализованный Content Profile в канонической JSON Schema.

Необходимо различать:

```
schema_version
≠
record_type_version
≠
record_version
```

Изменение конкретной Record не меняет версию типа.

Изменение JSON Schema не обязательно меняет семантику типа.

Изменение нормативного смысла типа требует контролируемого изменения его версии.

---

## 11. Статусы типов

Для каждого типа реестр должен различать как минимум:

- `registered` — тип нормативно зарегистрирован;
- `implemented` — для типа существует машиночитаемый Content Profile;
- `deprecated` — тип выведен из текущего использования, но исторически сохраняется.

На текущем этапе 19 типов зарегистрированы и все 19 имеют реализованный Content Profile в канонической JSON Schema.

Жизненный статус типа не равен статусу Record.

Возможные статусы типа:

```
proposed
draft
active
deprecated
superseded
archived
```

В первой реализации достаточно:

- `active`;
- `deprecated`;
- `superseded`;
- `archived`.

Статус типа должен позволять сохранить старые данные даже после прекращения использования типа для новых Record.

---

## 12. Совместимость

Изменение типа должно классифицироваться отдельно от изменения Record.

Возможны:

- исправление технического ограничения без изменения смысла;
- расширение без нарушения старых данных;
- изменение обязательности;
- изменение допустимых значений;
- семантическое изменение;
- разделение типа;
- объединение типов.

Последние два случая требуют особой осторожности.

Объединение типов не должно уничтожать информацию о прежнем типе.

Разделение типа не должно заставлять исторические Record выглядеть так, будто они изначально принадлежали новому типу.

---

## 13. Unknown type

Неизвестный `record_type` не должен автоматически трактоваться как:

- ошибка содержания;
- недействительная Record;
- неизвестный Referent;
- ложное утверждение.

Validator должен различать как минимум:

```
известный зарегистрированный тип
неизвестный тип
известный, но неподдерживаемый тип
известный устаревший тип
```

Политика импорта должна по возможности сохранять неизвестный тип как данные, даже если текущая реализация не может его валидировать или редактировать.

---

## 14. Запрет автоматического вывода типа

Следующие эвристики не являются каноническими:

```
файл *.claim.json → claim
папка /events/ → event
заголовок "Событие" → event
наличие поля "steps" → process
наличие поля "result" → result
```

Они могут использоваться интерфейсом как подсказки, но не как источник нормативной идентичности.

---

## 15. Требования к будущему Type Registry

Машиночитаемый реестр должен содержать для каждого типа минимум:

```
type_id
type_version
label_ru
standard
status
content_schema
allowed_references
migration_policy
```

Дополнительно могут быть:

```
description
aliases
deprecated_since
superseded_by
documentation
examples
```

Русское название является представлением для человека и не является машинной идентичностью типа.

---

## 16. Разделение реестра и JSON Schema

Этот документ является нормативной архитектурой реестра.

Конкретное машиночитаемое представление реестра будет определено вместе с JSON Schema.

Нельзя дублировать одну и ту же нормативную семантику в нескольких местах без правила, определяющего источник истины.

Предпочтительная цепочка:

```
Standard
   ↓
Type Registry
   ↓
Content Schema
   ↓
Validator
```

При расхождении технических артефактов нормативный Standard имеет приоритет до принятия отдельного архитектурного решения.

---

## 17. Entity Discipline

Перед добавлением нового типа необходимо пройти проверку:

1. Это действительно новый тип записи?
2. Или это семантическая роль?
3. Или это Referent?
4. Или это Context/Scope?
5. Или это отношение между существующими Record?
6. Можно ли выразить смысл существующим типом без потери информации?

Если существующего типа достаточно, новый фундаментальный тип не создаётся.

---

## 18. Критерии добавления нового типа

Новый тип может быть добавлен только при наличии:

- чёткой семантической ответственности;
- отличия от существующих типов;
- нормативного источника;
- обязательного набора содержательных ограничений;
- правил ссылок;
- правил версионирования;
- правил миграции;
- тестовых примеров;
- проверки на Entity Explosion.

Само наличие нового предметного домена не является достаточным основанием для создания нового типа.

---

## 19. Критерии готовности реестра

Реестр считается готовым к использованию первой JSON Schema, если:

- все текущие Standard 001–019 представлены;
- идентификаторы типов однозначны;
- нет двух типов с одной нормативной ответственностью;
- типы не смешаны с Referent;
- типы не смешаны с semantic role;
- типы не создают новых Core Entities;
- версии типов отделены от версий Record и схемы;
- неизвестные и устаревшие типы не уничтожают исторические данные;
- ссылки будут определяться нормативно, а не эвристически;
- русские названия не используются как машинные идентификаторы;
- реестр согласован с IMPLEMENTATION/000, 001 и 002.

---

## 20. Статус

Версия 0.1 является рабочим реестром типов проекта.

Следующий этап:

```
Type Registry
    ↓

    ↓

```

Реестр не заменяет специализированные Standards и не изменяет их семантику.
