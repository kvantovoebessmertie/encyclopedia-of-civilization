# Authoring Contract — контракт создания содержательных записей

Статус: рабочая операционная инструкция Фазы 1.

Этот документ не изменяет FOUNDATION, STANDARD или IMPLEMENTATION 000–021. При конфликте нормативные документы имеют приоритет.

## 1. Цель

Каждая новая запись должна быть:

- идентифицируема;
- версионируема;
- проверяема;
- связана с происхождением;
- ограничена областью применимости;
- честно представлять неизвестность;
- пригодна для последующей публикации и offline-восстановления.

## 2. Базовый процесс

```
вопрос / предмет
    ↓
поиск и фиксация источника
    ↓
выбор типа Record
    ↓
создание Content
    ↓
Scope / Context при необходимости
    ↓
Provenance
    ↓
Evidence Use / Assessment / Inference при необходимости
    ↓
Validator
    ↓
Semantic Conformance
    ↓
review
    ↓
publication
    ↓
package
    ↓
recovery
```

## 3. Выбор типа

Тип выбирается явно.

Нельзя выводить тип из:

- имени файла;
- папки;
- заголовка;
- наличия отдельных полей;
- текста записи.

Новый предметный домен не является основанием для нового Record type.

Перед созданием нового типа необходимо пройти Entity Discipline из IMPLEMENTATION/003-TYPE-REGISTRY.md и, если существующих типов недостаточно, оформить ADR.

## 4. Source прежде Claim, когда это возможно

Для проверяемого нового Claim предпочтительно сначала создать Record источника или зафиксировать внешний источник в Provenance.

Источник не является автоматически доказательством Claim.

Необходимо отдельно создать Evidence Use, если материал источника используется как свидетельство относительно Claim.

## 5. Claim

Claim должен содержать:

- самостоятельное пропозициональное утверждение;
- явный claim_type;
- ограничения, если без них меняется смысл;
- Scope / Context, если они существенны.

Нельзя расширять Claim выводами, которых источник или доказательства не поддерживают.

## 6. Evidence Use

Evidence Use должен различать:

- какой Claim рассматривается;
- какой Source используется;
- какой материал источника используется;
- поддерживает ли материал Claim или противоречит ему.

Evidence Use не является доказательством истинности сам по себе.

## 7. Неизвестность

Нельзя заменять неизвестное:

- догадкой;
- пустой строкой;
- произвольным null;
- текущим значением по умолчанию.

Если неизвестность семантически значима, используется предусмотренная схемой структура unknown status.

Различаются как минимум:

- unknown;
- absent;
- not_applicable;
- not_observed;
- not_recorded.

## 8. Scope и Context

Scope отвечает за область применимости.

Context отвечает за условия интерпретации или применения.

Они не должны смешиваться только потому, что оба являются Record references.

## 9. Provenance

Provenance должна позволять восстановить происхождение записи настолько, насколько это известно.

Происхождение не доказывает истинность содержания.

Авторство, provenance, ответственность и права не следует считать одним и тем же.

## 10. Версии

Изменение содержания не должно незаметно уничтожать предыдущую версию.

При существенном изменении:

- сохраняется record_id;
- создаётся новая record_version;
- фиксируется причина изменения;
- сохраняется связь происхождения;
- выполняется regression validation.

Нельзя переписывать историю ради получения PASS.

## 11. Completion и Publication

`completion_status` и `publication_status` независимы.

Published не означает complete.

Complete не означает true.

Draft не означает false.

## 12. Практические и опасные знания

Для процедур и действий необходимо отдельно учитывать:

- условия;
- необходимые ресурсы;
- ограничения;
- риск;
- уровень подготовки;
- критерий результата;
- область применимости.

Нельзя превращать наличие инструкции в утверждение о наличии способности.

Опасное практическое содержание должно проходить усиленную проверку до публикации.

## 13. Готовность записи

Record не считается готовой только потому, что JSON Schema её принимает.

Минимальные уровни:

### Structural

Record соответствует схеме.

### Semantic

Содержание соответствует применимым правилам Standard.

### Provenance

Происхождение зафиксировано настолько, насколько возможно.

### Publication

Производное представление не изменяет смысл Record.

### Recovery

Record может быть восстановлена из канонического пакета без незаявленной зависимости от исходной платформы.

## 14. Запрещённые shortcuts

Нельзя:

- считать validation доказательством истины;
- считать publication доказательством качества;
- считать provenance доказательством истинности;
- считать integrity доказательством истинности;
- считать trust доказательством истинности;
- превращать unknown в отрицательное утверждение;
- превращать отсутствие записи в отсутствие факта;
- удалять historical evidence;
- создавать новый type только для удобства предметного домена.

## 15. Definition of Done для первого вертикального среза

Первый предметный срез готов только если:

- все Record проходят Schema validation;
- ссылки и типы согласованы;
- semantic tests проходят;
- источники и Evidence Use различимы;
- Scope / Context не потеряны;
- Provenance присутствует;
- история версий сохраняется;
- publication output проверен;
- package integrity проверена;
- recovery выполнен;
- offline sufficiency проверена;
- итоговый evidence сохранён в audit trail.
